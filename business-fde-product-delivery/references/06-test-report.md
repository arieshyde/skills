# 交付物规范 06：测试报告 / 评估结果

Step 6 产出物 ｜ 负责：研发（R&D），Business+FDE 参与体验目标判定 ｜ 交接标准：关键指标达标 / 评估闭环跑通

## 一、做成什么样

验证「功能是否真正达到客户体验目标」的报告——不只是「跑通」。传统功能测试 + AI 产品评估两块内容按产品类型选择：

1. **传统功能测试报告**：测试范围、用例与结果、缺陷清单（级别、复现步骤、状态）
2. **AI 产品评估报告**（凡涉及大模型/检索/推荐的产品必须有）：离线评估闭环——数据集、任务、评估器三要素齐全，给出量化指标与回归基线

## 二、AI 产品评估的通用做法

1. **评估器分层**（多层混用，不靠单一方法）：
   - 确定性校验器：格式、长度、必含字段、规则命中——先跑，便宜且确定
   - 大模型评审（LLM-as-judge）：按评分量规对输出打分或两两比较，适合无唯一答案的场景；记录评审模型、版本、提示、采样设置和重复运行结果
   - 人工复核：用覆盖高风险、边界和随机样本的抽样校验评审器；抽样比例按风险和稳定性决定，不预设一个通用数字
   - 有参考答案的任务可加规则化指标（如检索命中率），与参考文本的重叠度类指标仅作辅助
2. **数据集**：从真实场景/历史数据构建测试集，标注输入与期望；测试集纳入版本管理，每次变更前后用同一测试集对比（防劣化）
3. **分层评估点**：
   - 检索增强类（RAG）：检索与生成分开评分——检索命中是前提，生成质量另评
   - 智能体（agent）类：任务完成率、步骤效率、工具调用正确性、规划遵循度
   - 排序/推荐类：排序质量（用位置加权或成对偏好指标）
   - 主观体验指标量化：把「回答质量」拆成可打分的量规项（准确性、完整性、简洁性各 1-5 分）
4. **回归纪律**：改提示词、换模型、调参数的每次变更都跑测试集；小的变更跑快速子集（确定性校验器+小样本评审），大的变更跑全量
5. **指标挂业务**：技术指标要对应到 PRD 的成功/失败判定指标与业务口径（专家一致率、命中率等合同指标在此阶段验证）

## 三、报告结构

1. 测试范围与版本（代码版本、测试集版本、被测配置）
2. 用例/评估任务清单与结果汇总（通过/失败/跳过，量化指标表）
3. 评估方法说明：用了哪些评估器、评分量规定义、人工复核比例
4. 指标对照：实测值对 PRD 判定指标逐条对照（达标/未达标/缺口）
5. 缺陷与问题清单：级别（阻塞/严重/一般/轻微）、复现、状态、责任归属
6. 结论与放行建议：可发布 / 修复后发布 / 不可发布及原因
7. 回归基线存档：本次指标作为下轮对比基线

## 四、怎么做

1. 从 PRD 的成功/失败判定指标反推测试与评估计划（指标先行，不是测完再找指标）
2. 构建有代表性的测试集与评分量规；避免训练/开发样本泄漏到独立验收集。量规先试评校准，记录人工与自动评审的一致性和分歧
3. 确定性校验器先行，再跑大模型评审，最后人工抽评
4. 结果对照 PRD 指标逐条判定；未达标项定位原因（数据/提示/模型/设计假设错误——最后一种触发回 Step 1/3）
5. 缺陷分级入清单；结论写放行建议，交 Step 7 决策
6. 立档：报告与测试集版本入库，供 ISO 体系审计与后续回归

## 五、标准要求

1. 进入发布执行的门槛：本次发布范围的 PRD 关键指标达标且有证据；适用的评估闭环真实跑通并可复跑。未达标结果仍可上会讨论修复、缩小范围或停止，不得标为已达标
2. 每条 PRD 判定指标都有对应实测值——无对照的测试不算完成
3. 缺陷清单分级完整；本次发布范围的阻塞级缺陷必须清零。延期或排除缺陷须有权人批准范围调整，记录影响并重新核对剩余范围的指标，不以一条豁免理由替代放行条件
4. 大模型评审的量规、评审配置和抽样复核结果已附在报告中，他人可复现并理解其不确定性
5. 测试集纳入版本管理

## 六、关键点

1. 「能跑通」与「达到体验目标」是两回事——本步验证的是后者；把演示当测试是 AI 产品最常见的自欺
2. 防劣化优先于提优：没有回归基线，每次「优化」都可能在别处悄悄变差（离线评估闭环存在的意义）
3. 大模型评审本身有噪声：量规模糊、评审不稳定时先修量规再重跑；关键结论加人工复核
4. 未达标时区分三种原因：实现问题（改代码）、评估问题（修量规）、设计假设错误（回 PRD）——第三种最宝贵，是 Working Backwards 闭环的真正触发点
5. 立档要求来自公司质量体系：测试报告留档、至少两人知晓结果
