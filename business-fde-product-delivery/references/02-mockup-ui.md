# 交付物规范 02：Mockup UI 原型与设计说明文档

Step 2 产出物 ｜ 负责：Business+FDE ｜ 交接标准：关键交互路径评审通过

## 一、做成什么样

两个交付物配套交付：

1. **可点击交互原型**：可用 HTML/JavaScript、Figma 或项目合适的工具。模拟真实使用流程：屏幕间可点击跳转，输入可触发状态变化。工期按路径数量、保真度和风险估算，不预设“两三小时”
2. **设计说明文档**：说明信息架构、交互逻辑与标注，与原型互相引用

定位纪律：原型验证交互与信息架构，不锁定技术实现。

## 二、可点击原型的内容要求

1. 覆盖 PRD 中全部关键交互路径（客户达成核心利益的完整操作流，例如「从进入页面到完成一次任务提交拿到结果」）
2. 每个关键屏幕检查适用状态：空数据、加载中、成功、错误/失败、权限不足或需要人工介入。不适用的状态注明原因，不机械凑齐
3. 用有代表性的场景内容，不用无意义占位文字。真实客户数据只有在已授权、已脱敏且符合数据处理要求时使用；否则使用明确标注的合成数据
4. 对客文案中不放不确定的承诺（耗时数字、效果数字），只放有把握的
5. 原型页脚或首页醒目标注「一次性原型，请勿用于生产」（THROWAWAY PROTOTYPE）

## 三、设计说明文档的结构

1. 信息架构总览：屏幕清单、层级关系（可用 Mermaid 图）
2. 用户流程图：每条关键交互路径的步骤序列，标注入口与出口
3. 屏幕逐屏说明：每屏的目的、关键元素、进出的条件
4. 交互标注（写在对应屏幕旁，说明图上看不出歧义的细节）：
   - 视觉类：字号、行距、颜色、间距、层级
   - 交互类：点击/悬停效果、元素激活与非激活条件、反馈时长
   - 功能类：数据来源、过滤排序规则、边界行为
5. 状态矩阵：每屏与适用状态的对照，不适用项说明原因
6. 与 PRD 的映射：每条功能范围条目对应哪些屏幕（反向校验无遗漏）
7. 客户评审记录：逐条留痕（日期、参与人、意见、处理结果）

标注原则：开发者可能问「如果……会怎样」的地方，都要写出来；说明文档持续增量更新。

## 四、怎么做

1. 从 PRD 的功能范围与用户故事出发，先画用户流程图（纸上或白板即可）
2. 挑出关键交互路径，列出屏幕清单，标出哪些屏属于 MVP 边界内
3. 用合适工具生成可点击原型。已有团队 UI/UX 标准时先读取并遵循；没有时先确定信息架构、关键路径和保真度。视觉不必精美，结构、状态和业务语义必须可信
4. 补全适用状态，使用有依据的场景和明确标注的合成演示数据
5. 沉淀设计说明文档（流程图、逐屏说明、标注）
6. 由用户或用户指定的业务负责人带原型与客户面对面评审：演示关键路径，让客户亲手点击；本技能事前准备评审材料包（原型、演示脚本、意见记录表），事后整理意见、逐条留痕并回写
7. 按评审意见修改原型与说明；实现细节问题回写设计说明，范围、客户价值或关键假设问题回产品发现技能更新 PRD 与台账，再继续迭代
8. 内部研发预审一轮（提前暴露实现疑问），评审通过后进入 Step 3

## 五、标准要求

1. 交接标准：关键交互路径已由目标用户或业务代表实际操作并形成证据；主要问题已处理或明确接受。不要把礼貌性的“满意”当成验证
2. 本次范围内涉及界面的 PRD 条目均有屏幕映射；后台任务或接口等非界面需求说明验证方式，不强造屏幕
3. 适用状态覆盖关键屏幕；演示数据不冒充客户事实
4. 「一次性原型，请勿用于生产」标注在位
5. 客户评审记录完整留痕，未处理意见有去向说明
6. 设计说明文档随原型演进同步更新（活文档）

## 六、关键点

1. 原型代码默认不进入生产。若团队决定复用，必须作为新的工程实现接受完整代码审查、测试、安全与运维检查，不能因来源是原型而跳过
2. 原型用于尽早发现方向错误；节省的工期和成本按项目证据估算，不预设固定小时或周数
3. 只演示不让人上手点击等于没验证；客户亲手操作暴露的问题远多于观看
4. 空态/错误态是最容易偷懒的地方，也是客户体验最先破裂的地方
5. 评审意见逐条留痕，可追溯到日期与参与人，作为后续复盘的证据链
6. 不要在原型上过度打磨视觉细节；验证对象是交互与信息架构，不是美术
