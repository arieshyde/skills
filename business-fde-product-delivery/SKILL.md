# Business+FDE 产品交付

版本：1.2.0（2026-09-29）。本目录的参考规范随本技能整体版本管理，与产品发现技能 1.2.0 配套。

## 目的与边界

- 承接 `business-fde-product-discovery` 以 Working Backwards 为核心产出的产品定义及真实裁决，把已定义的客户体验交付为可验证的产品；交付阶段各环节的交付物仍围绕 Working Backwards 定义的客户体验实现。这套交付闭环属于团队落地约定，不应称为 Amazon/AWS Working Backwards 的标准步骤。
- 本技能可起草文档、生成一次性原型或代码、检查范围一致性、整理反馈并持续维护文档。
- 裁决权分工：客户触达、承诺、签字、发布和放行由用户或用户指定的业务负责人执行；技术可行性、任务归属和代码质量由用户指定的研发负责人确认。本技能不代替用户或相关负责人作批准决定。

## 硬规则

全程生效。本文件其他章节只引用编号，不重复表述；规则细节由参考规范展开，同一规则不得出现两种表述。

- **H1 不得虚构。** 不得虚构项目现状、需求或验收结论，不得自行发明需求后继续执行。负责人、期限无依据时写“拟请会议确定”。文档只写实质信息，不得为了满足模板要求而制造“零风险、零偏差、零遗留”等虚假结论。
- **H2 范围一致。** 设计、任务、测试和发布内容必须符合已确认的 PRD 或已批准的变更。无法说明必要性的内容标为待裁决，不得静默扩大范围；不要求另建逐项追溯表。
- **H3 主张状态。** 沿用发现阶段的六种状态：**已验证事实**、**有据估算**、**待验证假设**、**已批准决策**、**未来目标**、**未知待补**。
- **H4 指标与结果分离。** 客户结果指标、产品行为指标和工程性能指标分开记录，不得用“系统跑通”代替客户结果。目标、实测结果和解释分开记录；不得通过改写目标让测试失败“消失”。
- **H5 编号按需使用。** 新项目默认不建立跨文档编号体系。项目已有稳定的编号体系，或编号确实有助于任务、测试和缺陷管理时可以沿用；不得为了满足模板要求而新增编号，也不得让编号成为理解正文的前提。
- **H6 原始材料与来源展示。** 原始客户反馈保持原貌。派生的技术设计、任务、测试、发布和复盘文档默认只在文末集中列出主要来源文件，不逐项复制原始页码、行号和时间戳。三种情况除外：用户明确要求、处理事故或争议、直接引用合同或法规原文。
- **H7 拟议与合成数据显式标注。** 设计中新增的接口和数据模型标为拟议，并说明各自服务于哪项已批准需求。演示用合成数据须显式标注，不得作为真实客户数据或验证证据。范例数字、时间估算和工具选择仅作参考提示，不是项目事实；没有本项目依据时不给出精确承诺。
- **H8 文档不隐含授权。** 任何阶段文档都不得隐含授权部署或发布。交接标准用于约束实际执行，不妨碍如实准备包含失败、未完成或待议事项的上会稿。

## 输入门槛

准备评审材料时可以记录缺口和拟议方案；开始执行相应交付工作前必须同时具备：

1. 已确认或有条件确认的 PRD，含范围、非目标、指标和依赖。
2. 关键原始材料、假设与裁决记录。
3. 针对完整交付：获批范围内阻断项清零，且前置条件满足。

有条件通过时，只开展裁决明确允许且前置条件已满足的工作，其他部分暂停；核心价值待验证时，只按已批准的验证范围开展 PoC，不得扩大为完整交付。

执行输入不满足时：

1. 指出缺口。产品定义缺口回到 `business-fde-product-discovery`；工程资料缺口在本阶段补充。
2. 仍可准备用于讨论缺口的评审材料，但不得违反 H1 推进执行。
3. 项目为空或资料不完整时，先列出已找到的材料和缺口，引导用户补充 PRD、关键原始材料、裁决、技术约束及交付目标。暂不能补齐时，可准备资料清单、调研问题或拟议验证计划；已有信息足以确定议题时，可形成讨论缺口的上会稿。
4. 用户本轮输入与已确认的客户、范围、阶段、术语或技术现状明显不符时：先指出具体冲突和可能影响，请用户确认这是变更、误贴还是用词问题。影响范围或产品含义的内容在确认前不得进入设计、任务和实现；明显笔误可提出修正建议，但不得静默改变业务含义。

## 变更控制

1. 新需求或范围变化：先记录来源、影响、主张状态和建议的处理方式。
2. 影响客户、首要收益、核心范围、对外承诺或关键指标的变化：回到 `business-fde-product-discovery` 更新 FAQ/PRD 中受影响的内容并取得裁决。
3. 纯实现细节变化：可在技术设计与实施总结中裁决，但必须说明影响与验证方式。
4. 被否决的方案和重要偏差须记录否决理由，避免后续重复试错。

## 输出约定

所有文档统一用于上会评审，不得以工作底稿或对外成稿为名另设多份版本；不同交付物按各自用途保留。材料就绪不代表项目获批、测试通过或发布放行。

1. 主评审文档开头写明：会议目的、建议结论、待决策事项、关键依据和主要风险；按议题补充资源与备选方案。同一次会议只保留一处完整摘要，配套文件直接引用，不另增汇总文件。未知或失败结果可以上会，但要说明影响和下一步。建议结论与真实裁决分开；批准人、日期、范围和条件只按真实记录填写。
2. 交稿前检查：术语解释、事实与建议的区分、主要来源的可访问性、残留的模板用语。空白占位符改为具体待议问题，不得编造内容填补；删除不必要的编号、时间戳和重复来源说明。使用 Word、PDF 或演示文稿时，检查渲染后的分页、表格、图示与可读性。
3. 服从项目已有的目录与命名规范；项目没有规范时，再建议 `YYYYMMDD-S<阶段号>-项目关键字-交付物.md`（阶段号取实际 Step 编号）。
4. 原始客户材料按 H6 处理。
5. 原型代码默认按一次性使用处理，不直接进入生产；决定复用时，须作为新的工程实现接受完整的代码审查、测试和安全检查。
6. 项目已有需求、任务、测试或缺陷编号体系时，服从项目规范；项目没有编号体系时，不为本技能另建一套。
7. 每次交接同时给出：完成项、证据、偏差、未决项、阻断项和下一责任人。

## 完成标准

以下为实际阶段工作的完成标准，不作为提交评审材料的前置条件。阶段工作尚未完成时，如实报告未完成内容、失败结果和待决策事项，不得伪造达标结论（H1）。

- [ ] 设计、任务、实现、测试和发布内容与已批准范围一致 [H2]
- [ ] 关键客户结果和风险均有可复现的验证证据 [H4]
- [ ] 实现与设计/原型的偏差已记录、评估并裁决
- [ ] 发布有明确的范围、回滚方案、观察指标和负责人
- [ ] 复盘按原始目标核对结果；问题已回写到正确的上游文档
- [ ] 输入缺口和内容冲突已提示并得到处理，没有通过虚构内容推进交付 [H1]
- [ ] 没有为了满足模板要求而建立编号或追溯体系，正文没有不必要的精确来源定位 [H5/H6]
