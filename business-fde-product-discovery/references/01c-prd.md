# PRD：把产品定义落成可评审的边界

PRD 说明要做成什么、为什么、如何验收。它从有据可查的五问、PR 和 FAQ 派生；拟议范围与已批准范围分开，不得悄悄新增无来源需求。

## 一、输入门槛

1. 原始材料保持原貌并可访问。
2. PR 与 FAQ 已形成可供本次会议讨论的内容，关键未知及其影响已列明。
3. 客户、核心问题、首要收益、主要范围和关键假设已形成一致口径。
4. 若关键价值仍待验证，PRD 只能定义验证性 PoC，不得伪装成完整产品承诺。

## 二、建议结构

1. 背景与机会：问题、影响和可追溯来源。
2. 客户与角色：主客户、用户、付款人、受影响者。
3. 当前旅程与目标体验：当前摩擦及希望发生的变化。
4. 产品定义：一句话说明为谁解决什么问题、带来什么首要收益。
5. 范围：本阶段做什么；每项链接到问题、收益、法规义务或批准决策。
6. 非目标：明确不做什么、为什么、何时可能复评。
7. 用户旅程或关键场景：正常、异常与人工介入路径。
8. 成功与失败指标：定义、基线、目标、单位、分母、时间窗、数据来源和负责人。
9. 假设与验证：写清关键假设、验证方式和失败影响，不复制出第二套事实。
10. 依赖与约束：客户、平台、第三方、法规、资源和时间窗。
11. 开放问题与阻断项：状态、负责人、期限和影响。
12. 变更记录与批准记录。

新项目默认不建立主张、假设、冲突或来源编号。项目已有稳定需求编号时可以保留，但自然语言标题和内容必须能脱离编号独立理解。

## 三、来源规则

不同类型的需求使用不同的可追溯来源：客户需求来自客户证据；法规要求来自正式文件；技术约束来自测试或研发确认；范围和优先级来自具名裁决。不得强迫所有条目都伪装成客户会议原话。

客户提出的解决方案先追问目标，但不擅自改写其意图。客户原话保留在原始材料中；PRD 记录 Working Backwards 倒推出的结论、依据和仍存在的解释风险。

主要来源默认在文末集中列出文件名或可访问链接，不在每个范围条目和表格行中重复。默认不写会议发言时间点、页码和行号；三种情况除外：用户明确要求、直接引用合同或法规原文、处理来源争议。

## 四、指标规则

1. 没有基线时先定义测量方法；不得复制历史范例中的数字。
2. 客户结果指标、产品行为指标和工程性能指标分开记录。
3. 目标值标明“已同意目标”或“待验证目标”；不得把工程内部目标写成客户承诺。
4. 指标必须能在交付技能的测试与发布后观察中复测。

## 五、交接门槛

以下约束用于从评审转入执行，不阻止包含待议事项的 PRD 上会。未批准范围标为拟议；有条件通过仅允许开展明确获准且前置条件满足的工作，待验证时仅按获批验证范围开展 PoC。

- 范围与非目标清晰，且业务负责人已确认或明确条件。
- 每项范围有可追溯来源和验收方式，无悬空需求。
- 关键指标定义完整，不用形容词代替判据。
- 拟进入执行的获批范围内阻断项清零；验证性 PoC 可以检验尚未证实的核心假设，但其自身执行前置条件必须满足。非阻断性未知项有负责人、期限和接受记录。
- 与 PR、FAQ 的一致性检查通过。
- 交接时提供 PRD、关键原始材料与裁决记录，供 `business-fde-product-delivery` 使用。

## 六、既有 PRD 的评审与修改更新（升版）

对项目仓库中已成文的 PRD 先评审、再修改更新并生成新版本文件时，按以下步骤执行。

1. 读当前版全文（含版本变更表和来源章节），与上一版 diff 确认最近变化。版本变更表中已删除的内容不得重新加回。
2. 文档定位判定。来源章节显示多数需求条目出自内部设计问答（无客户参与、无逐项批准记录），且文档实际用途是与客户讨论功能点、指导原型（mockup）生成时：停止按合同级 PRD 升版，改为拆分处理。
   - 原文档按实际用途更名（如「功能需求清单与原型规格」）；文档头与来源章节标明条目为拟议设计。
   - 主要来源写清文件名和日期；不得用「本轮问答」这类指向不明来源的表述充当确认记录。参与人只在判断授权或裁决效力确有必要时记录。
   - 按第二节结构新建合同级 PRD，范围拆为三层：已确认决策、拟议待客户逐项确认、开放问题。
   - 原「全部属合同范围」类表述列为未解决冲突，并给出按三层拆分的建议结论。
   - 拆分时既有需求条目编号与内容不变。
   - PR、FAQ 的引用与范围口径同步改指新文件；修改后用 grep 自检旧文件名与旧口径是否残留。
3. 覆盖审核（双向）：
   - 正向：顺着来源章节找到原始需求材料（访谈梳理、会议纪要），逐条核对客户已提出但未写入的需求或开放问题。
   - 反向：核对范围与交付表述是否有具名裁决或客户逐项确认支持（如「全部属于合同一期范围」「须完整实现」）；不得把上一版的范围断言当作既成事实沿用。
   - 只有方向性认可而无逐项裁决时，将相关表述降级为拟议；与来源冲突的内容列入未解决冲突。
4. 内部一致性审核至少检查四类：
   - 全文术语统一：同一角色/对象只有一个正式名称。
   - 跨条目清单对齐：如成果文件类型须在任务、文件空间、能力清单条目中一致。
   - 角色总览表与各章条目中的职责一致。
   - 项目已有条目编号时，页面清单与交付范围引用的编号必须真实存在且范围匹配。
5. 分流规则：
   - 客户已确认且细节明确：新增需求条目，默认行为用「应」级措辞，并在文末“主要来源”中列明其依据。
   - 客户已提方向但规则未定：列入开放问题，不写成功能需求。
   - 量化指标未商定：不虚构数值，商定后回写。
6. 编号纪律：项目已有条目编号时一律不改、不重排，新条目按项目原规则追加；项目没有编号时不为本次评审新建编号体系。
7. 保存为新版本号文件，旧版原样保留；第 2 条的拆分路径为更名加新建，不受本条限制。同步更新版本变更表、主要来源和页面清单等全部受影响章节。修改后用 grep 自检新条目、版本号与旧术语残留。
8. 汇报时分列：修复的不一致项、补入的遗漏项（含分流去向）、未动的部分及理由；不重述文档结构。
