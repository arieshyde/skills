# PR：未来新闻稿

PR 站在未来发布时点描述客户将获得的价值，属于 Working Backwards 核心产物；它是产品定义与对齐工具，不是对外发布授权。真实对外新闻稿需要另行审定。

PR 必须是独立文件，不与 FAQ 合并。若当前信息不足以形成可信的客户、问题和首要收益，先返回资料缺口与澄清问题；不得用虚构场景拼出一篇完整新闻稿。

## 一、PR 要回答清楚的问题

1. 谁会因这个产品而改变行为。
2. 该客户的当前问题为什么值得解决。
3. 产品带来的唯一首要收益是什么。
4. 目标体验如何优于当前替代方案。
5. 客户如何开始使用并获得价值。

## 二、推荐结构

结构按内容需要取舍，不为凑模板增加段落：

1. 标题：产品或服务、目标客户、首要收益。
2. 副标题或一句话摘要：补充适用场景与变化。
3. 设想发布日期与地点：有依据时标注为拟议；未知且与议题有关时写“拟请会议确定”，无关时省略，不保留空白占位符。
4. 摘要：宣布什么、为谁、解决什么、为何重要。
5. 问题：不提方案也能让目标客户认出自己的处境。
6. 方案与目标体验：客户如何获得价值，避免技术实现主导叙事。
7. 公司引语：有真实来源时引用；自行拟写的内容标为“拟议表述，待确认”，不得冒充已批准承诺或真实发言。
8. 假想客户引语：仅用于检验客户是否会这样描述收益；必须标注“假想引语”。
9. 如何开始与下一步：适用于该产品的采用路径。

正文不为证据管理目的增加主张编号、来源定位或方法论说明；PR 承诺所需的依据、假设和风险说明由 FAQ 承担。

不是每篇 PR 都必须包含地点、渠道、SEO、完整 5W1H 或行动号召。这些属于写作选择，不是 AWS 方法的统一硬性要求。

## 三、准确性规则

1. PR 写未来目标，不得把尚未实现的能力写成当前事实。
2. 事实与数字必须有可靠来源；内部目标、工程目标和客户承诺分开表述。
3. 假想客户引语不得使用真实客户名、企业名或可识别职位，不得作为需求证据。
4. “显著、革命性、领先、大幅、赋能”等无法验证的修饰词，删除或改为有依据的事实表述。
5. 写差异化时与当前替代方案比较，说明比较维度和证据状态；没有量级依据时不得编造数字。
6. PR 只承担价值主线。经济性、依赖、安全细节、风险与假设放入 FAQ，但 PR 不得与其冲突。

## 四、篇幅原则

不设固定页数。目标是用最短篇幅完整说清客户、问题、首要收益和体验：

- 能删除而不损失关键信息的内容就删。
- 为压缩篇幅而删除证据边界、适用范围或关键限制则不合格。
- 篇幅过长通常说明主收益不唯一、背景过多或实现细节混入；先修主线，不机械调字号或砍必要信息。
- 评审场合需要篇幅预算时，由项目另行约定，不得将其冒充为 AWS 通用标准。

## 五、自检

- 标题、摘要、问题和方案是否围绕同一个首要收益。
- 行业外读者能否理解客户为何在意。
- 每项承诺能否在 FAQ 中找到依据、假设或风险说明。
- 是否把未来目标、估算或假设写成了既成事实。
- 是否出现未经标注的假想客户背书。
