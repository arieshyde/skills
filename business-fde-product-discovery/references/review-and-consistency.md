# 评审与跨文档一致性

## 一、产品定义不变量

五问、PR、FAQ、PRD 与产品定义台账必须共享：

1. 主客户、实际用户、付款人和受影响者。
2. 核心问题及当前替代方案。
3. 唯一首要收益。
4. 当前基线、目标值、单位和时间窗。
5. MVP 范围、非目标和适用边界。
6. 统一术语和名词定义。
7. 风险、假设编号与验证状态。

## 二、双向核对

1. PR 每项承诺在 FAQ 或台账中有证据、假设或风险说明。
2. FAQ 否定或限制的事项没有被 PR 反向承诺。
3. PRD 每项范围都对应客户问题、收益、法规义务或经批准决策。
4. PRD 不增加未经评审的新客户需求；技术实现偏好不伪装成客户需求。
5. 同一指标在不同文档中的定义、数值、分母、时间窗和适用范围一致。
6. 同一概念只用一个正式名称；别名集中记录，不在正文漂移。

## 三、评审结论

本规范用于统一的上会评审稿。主评审文档开头集中说明会议目的、建议结论、待决策事项、关键依据、主要风险，按议题补充备选方案与资源需求；配套文档引用该摘要。材料就绪表示能够支持本次讨论，不表示产品验证通过或执行获批。

先判资格，再讨论细节：

1. 客户是否清楚。
2. 问题是否由证据支持。
3. 方案是否直接改善该问题。
4. 客户是否有理由改变行为、购买或采用。
5. 经济性、风险与依赖是否允许持续服务客户。

本次未裁决事项会前标为“建议结论”，实际裁决保持“未评审”；历史有效裁决保留。会后依据真实记录回写批准人、日期、范围和条件。建议及实际裁决使用以下四类：

- **通过**：关键主张可辩护，阻断项清零。
- **有条件通过**：条件、负责人、期限与复核点明确。
- **待验证**：核心假设未证实，暂不投入完整交付。
- **不推进**：理由和复评条件归档。

有条件通过仅允许推进裁决明确允许且前置条件已满足的工作；完整交付需获批范围内阻断项清零。待验证项目可上会申请限定范围的验证性 PoC，经批准后才执行，不推定已获完整交付授权。责任人、期限尚未确定时在评审稿写“拟请会议确定”，不据此声称执行条件已满足。

## 四、交接前检查

- 搜索所有 `TBD`、`待确认`、`未知`、占位日期和占位姓名，逐项确认是否允许留存。
- 搜索所有数字，检查来源状态与完整口径。
- 检查假想客户引语是否明确标注为假想。
- 检查每个来源是否存在、可访问、能定位到原文。
- 将冲突、失败检查和未决项单独报告；不得只汇报“已完成”。
- 检查所有缩写编号在每份面向读者的文档中均有“编号说明”，且首次出现时能看懂类别与用途。
- 检查 PR 与 FAQ 是两个独立文件，而不是合并文档。
- 检查本轮输入是否与项目主题、客户、阶段和术语一致；明显不搭或用词影响含义时，必须留下提醒与确认结果。
- 检查空白是否来自真实未知；不得用虚构场景、数字、人物或结论填满模板。
- 主摘要明确请会议决定什么；建议、已有决策和实测结果分别表述。
- 首次出现的专业术语有解释；正文保留必要依据与边界，详细追溯材料可放在同一文档的附件部分。
- 占位符转为具体待议问题，并说明对本次决策的影响；清除模板提示、写作指令和无内容的章节。
- 项目名、日期、版本及引用一致；Word、PDF 或演示文稿须检查渲染后的分页、表格截断、图示和字号。没有生成对应格式时不声称已完成版式检查。
