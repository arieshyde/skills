# Business+FDE 产品发现

版本：1.1.1（2026-09-25）。本目录的参考规范和模板随本技能整体版本管理，与产品交付技能 1.1.1 配套。

## 目的与边界

- 以 Amazon/AWS Working Backwards 的客户倒推机制为核心，服务 Business+FDE 模式的产品定义工作。
- 核心产物：五问、未来新闻稿（PR）、客户与内部 FAQ、PRD。原型及后续研发交付由 `business-fde-product-delivery` 承接。
- 两层内容分开表述：五问、未来 PR、FAQ 和以客户价值检验假设属于 Working Backwards 核心；PRD、文件命名、评审门槛和角色分工是团队落地约定，不称为 AWS 硬标准。
- 本技能只起草、核对、维护文档并准备评审材料。客户触达、承诺、裁决、签字、发送和放行由用户或用户指定的有权人执行。不替用户作批准决定；信息不足时不替用户补结论。

## 硬规则

全程生效。其他章节只引用编号，不重复表述。

- **H1 不得编造。** 不虚构客户、场景、痛点、数字、引语、竞品结论或内部决定来补齐正文。负责人或期限没有依据时，写“拟请会议确定”。
- **H2 假想引语显式标注。** 假想引语只能基于已明确的产品设想，逐处标注“假想引语，仅用于检验目标体验”，不得充当证据。不使用仿真的真实姓名、企业名或职位制造背书。
- **H3 主张状态。** 每项关键主张使用六种状态之一：`已验证事实`、`有据估算`、`待验证假设`、`已批准决策`、`未来目标`、`未知待补`。定义与来源规则见 [evidence-and-claims.md](references/evidence-and-claims.md)。
- **H4 数字纪律。** 没有来源的数字不得写成事实。数字注明单位、口径、基线、时间窗和适用范围；缺一项即标为估算或待验证。
- **H5 编号与行内引用。** 出现 `C-01`、`H-09` 等编号时，必须在目录后或首次出现前给读者可见的“编号说明”，列出本文件实际使用的类别，说明编号用于跨文档追溯。台账为每个编号登记唯一短题名（≤10 字）。正文引用一律“短题名（编号）”格式：FAQ 同条目重复出现后可只用短题名；PRD 条目标题自带编号、表格内编号与标题并排时格内可单用编号；PR 正文零编号，追溯由台账承担。单句引用超过 3 个编号时改列表。细则见 [evidence-and-claims.md](references/evidence-and-claims.md)。
- **H6 PR 与 FAQ 为两个文件。** 必须输出为两个独立文件并互相校验，不得合并成一个 PRFAQ 文件。客户 FAQ 与内部 FAQ 可为同一 FAQ 文件的两个章节。
- **H7 原始材料只进不改。** 引用会议或访谈时保留原说话人标识、时间戳和来源文件，不推断身份归属。
- **H8 历史范例仅供参考。** 项目目录中既有的历史范例不作为默认模板，也不自动读取。任何历史范例只参考结构和节奏，禁止复用其中事实、数字、客户引语和产品结论。
- **H9 冲突并列记录。** 发现来源冲突时，并列记录冲突双方、影响和待裁决人，不自行选取方便的一方。

## 输入盘点与适配检查

开始成文前执行：

1. 盘点用户输入和项目已有材料，区分“已有事实”“用户本轮补充”“仍缺资料”三类。不把文件夹名称、历史范例或常识扩写成项目事实。
2. 对没有内容或材料不足的项目，先说明当前能做什么、缺什么，再引导用户提供最小资料：项目目标或触发背景、目标客户/用户、已观察到的问题、原始证据位置、现有方案、约束与已有裁决。一次优先问最影响方向的问题；也可给一份便于填写的缺口清单。
3. 缺关键资料时，先提供资料清单、访谈提纲或待验证问题。已有信息足以明确本次议题时，可形成讨论补证、调整或停止的上会稿。正文遵守 H1。
4. 用户输入与项目名称、已有产品定义、术语表、阶段目标或证据明显不搭时：先指出具体冲突及其影响，请用户确认是新方向、误贴内容还是需要修改原项目定义。确认前不把冲突内容扩写为正式产物。
5. 用词疑似错误、歧义、夸大或把假设说成事实时：引用原词，说明问题，给一至两个候选改法。影响产品含义的词必须确认后再使用；不影响含义的明显笔误可直接修正，但简短说明。

## 准确性要求

1. 分清客户、实际用户、付款人和受影响者，不默认四者相同。
2. 客户需求只能由客户原话、行为、现场观察或客户数据支持。市场、法规和技术资料可补充背景，不能冒充客户证据。
3. PR、FAQ、PRD 共享同一套产品定义、术语、指标、范围和假设编号，按 [review-and-consistency.md](references/review-and-consistency.md) 校验。
4. 主张状态、数字、引语、编号与冲突处理按 H1–H5、H9 执行。

## 评审与阶段推进

文档统一用于上会评审，不按工作底稿或对外成稿另设多份版本。材料就绪与项目获批分别记录。

1. 材料可以带关键未知和阻断项上会，用于讨论是否验证、调整或停止。须说明未知对本次决策的影响、补证方式和建议。
2. 主评审文档开头写明：本次评审目的、建议结论、请会议决定的事项、关键依据和主要风险。资源投入与备选方案按议题需要提供。
3. 同一次会议只设一处完整摘要，配套文件引用该摘要，不重复生成汇总文件。PR 与 FAQ 配套时，通常在 FAQ 开头承载摘要。
4. 本技能提出的推进或取舍结论一律标为“建议”；事实核对与实测结果据实表述。真实裁决另记批准人、日期、范围、条件及依据。本次未裁决的事项保持“未评审”，保留历史有效裁决，不预填新的批准记录。
5. 完整交付须同时满足：有权人批准相应范围、该范围阻断项清零、前置条件满足。有条件通过时，只开展裁决明确允许且前置条件已满足的工作，未满足部分暂停。核心价值待验证时，只按已批准的验证范围开展 PoC，不扩为完整交付。

## 工作路由

按当前任务只读取需要的规范，不默认加载全部参考文件：

- 想法粗糙、证据不足或需要重新界定客户问题：读 [00-five-questions.md](references/00-five-questions.md)。
- 起草或评审未来新闻稿：读 [01a-pr-press-release.md](references/01a-pr-press-release.md)。
- 起草或评审客户/内部 FAQ、假设或 go/no-go：读 [01b-faq.md](references/01b-faq.md)。
- 将产品定义转为拟议或已批准的范围、非目标和验收指标，或审核升版项目仓库中既有 PRD：读 [01c-prd.md](references/01c-prd.md)。
- 任何成文或评审任务：同时读 [evidence-and-claims.md](references/evidence-and-claims.md) 和 [review-and-consistency.md](references/review-and-consistency.md)。

## 工作流

1. 确认项目目录、任务目标、本次会议目的和已有裁决。先完成上述输入盘点和适配检查：已有材料不重复制造，缺资料时先引导补充。
2. 建立或更新产品定义台账。新项目可复制 [product-definition-ledger.md](assets/product-definition-ledger.md)。
3. 用五问形成可辩护的客户、问题、首要收益、证据和目标体验。答不出的项进入验证计划。
4. 写 PR 与 FAQ。谁先写不作硬规定，但按 H6 输出为两个文件并互相校验。PR 聚焦客户价值；FAQ 承担细节、经济性、依赖、风险与假设。
5. 完成资格检查，提出 go/no-go 建议，列出待决策事项。实际裁决由用户或用户指定的有权人作出，会后按真实记录回写。
6. 按本次议题编制 PRD 评审内容。范围、非目标、指标和假设必须能回指产品定义及来源；未批准部分标为拟议。用于执行的范围须满足「评审与阶段推进」第 5 条。
7. 上会前执行跨文档一致性与可读性检查。未通过项、冲突与阻断项直接报告，说明各自阻断哪项决策或执行工作。

## 输出约定

1. 正文写入用户指定的项目目录，默认中文 Markdown。命名可沿用 `YYYYMMDD-S1-项目关键字-交付物.md`；项目已有规范时服从项目规范。
2. 同时产出 PR 与 FAQ 时的命名示例：`YYYYMMDD-S1-项目关键字-PR.md`、`YYYYMMDD-S1-项目关键字-FAQ.md`（文件分离要求见 H6）。
3. PR 不要求固定页数，以“完整表达核心客户价值且没有可删除内容”为准。篇幅过长时检查主线是否聚焦；不得为压页删除必要事实、边界或风险。
4. 正文之外另给简短自检结果：已验证、仍待验证、阻断项、跨文档冲突、输入适配性问题、建议裁决。

## 完成标准

交付前逐项核对；方括号内为规则出处：

- [ ] 客户、问题、首要收益和目标体验口径一致，各有对应证据或明确假设状态 [H3]
- [ ] PR 中每项承诺都能在 FAQ 或台账中找到支撑、假设或风险说明 [H3]
- [ ] FAQ 覆盖客户问题和内部问题；关键未知没有被伪装成确定答案 [H1]
- [ ] PRD 的范围、非目标和指标来自有来源的产品定义，拟议与已批准状态清楚 [H3/H4]
- [ ] go/no-go 建议及待决策事项明确；已有裁决按真实记录留痕；未开会不妨碍评审材料完成
- [ ] 跨文档一致性检查通过，或未通过项已明确阻断交接
- [ ] PR 与 FAQ 为两个独立文件；所有编号均有读者可见的类别说明，行内引用符合短题名格式 [H5/H6]
- [ ] 缺失资料和输入冲突已明确提示，没有用虚构内容填补 [H1]

## 补充调研与参数建议

用户要求为产品体验参数（时长、阈值、配比、并发量等）给出建议值，或整理补充调研文档时：按以下步骤执行。

1. 提建议值前先扫项目仓库现有素材：用术语关键词（阈值、静音、超时、时长、中断等）检索 01-requirements 各目录，确认既有设计基线、已定案参数和现网反馈，然后再检索外部文献。
2. 外部来源逐条抓原文核对，不凭搜索摘要采信。仅见于转载的数据，须两处独立来源或不同研究交叉佐证后才写入，并在文档中标注核验路径。
3. 既有基线与行业默认值冲突时，按本场景的错误代价取舍，写明行业默认值的标定场景与不适用原因，不直接套用行业默认值。
4. 交付物显式标注结论修正：原建议、现结论、原因。每个建议值附允许范围与上线后验证指标。
