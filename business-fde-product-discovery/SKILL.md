# Business+FDE 产品发现

版本：1.0.0（2026-09-21）。本目录的参考规范和模板随本技能整体版本管理，与产品交付技能 1.0.0 配套。

## 目的与边界

本技能以 Amazon/AWS Working Backwards 的客户倒推机制为核心，服务兆恒智能的 Business+FDE 产品定义工作。核心产物是五问、未来新闻稿（PR）、客户与内部 FAQ、PRD；原型及后续研发交付由 `business-fde-product-delivery` 承接。

AWS 核心与团队扩展分开表述：五问、未来 PR、客户/内部 FAQ 和以客户价值检验假设属于 Working Backwards 核心；PRD、文件命名、评审门槛和角色分工属于团队落地约定，不称为 AWS 硬标准。

本技能可起草、核对、维护文档并准备评审材料。涉及客户触达、承诺、裁决、签字、发送和放行时，由用户或用户指定的有权人执行；本技能不替用户作批准决定。信息不足时不得替用户补结论。

## 对话与输入门槛

1. 开始成文前先盘点用户输入和项目已有材料，区分“已有事实”“用户本轮补充”“仍缺资料”，不要把文件夹名称、历史范例或常识扩写成项目事实。
2. 对没有内容或材料不足的项目，先说明当前能做什么、缺什么，并引导用户提供最小资料：项目目标或触发背景、目标客户/用户、已观察到的问题、原始证据位置、现有方案、约束与已有裁决。一次优先询问最影响方向的问题；也可给用户一份便于填写的缺口清单。
3. 缺少关键资料时，先提供资料清单、访谈提纲或待验证问题。若已有信息足以明确本次议题，可形成讨论补证、调整或停止的上会稿；不得编造客户、场景、痛点、数字、引语、竞品结论或内部决定来补齐正文。仅供检验目标体验的假想引语须基于已明确的产品设想并显式标注，不得充当证据。
4. 若用户输入与项目名称、已有产品定义、术语表、阶段目标或证据明显不搭，先指出具体冲突及其影响，再请用户确认是新方向、误贴内容还是需要修改原项目定义。确认前不把冲突内容继续扩写为正式产物。
5. 若用词疑似错误、歧义、夸大或把假设说成事实，引用原词，说明问题，并给出一至两个候选改法。影响产品含义的词必须确认后再使用；不影响含义的明显笔误可修正，但要简短说明。

## 准确性纪律

1. 先分清客户、实际用户、付款人和受影响者；不能默认四者相同。
2. 每项关键主张标明状态：`已验证事实`、`有据估算`、`待验证假设`、`已批准决策`、`未来目标`、`未知待补`。状态定义与来源规则见 [evidence-and-claims.md](references/evidence-and-claims.md)。
3. 没有来源的数字不得写成事实；所有数字注明单位、口径、基线、时间窗和适用范围。缺一项就标为估算或待验证。
4. 客户需求只能由客户原话、行为、现场观察或客户数据支持；市场、法规和技术资料可以补充背景，不能冒充客户证据。
5. 假想客户引语必须显式标为“假想引语，仅用于检验目标体验”，不得使用仿真的真实姓名、企业名或职位制造背书。
6. 发现来源冲突时并列记录冲突、影响和待裁决人，不自行选取方便的一方。
7. PR、FAQ、PRD 必须共享同一套产品定义、术语、指标、范围和假设编号；按 [review-and-consistency.md](references/review-and-consistency.md) 校验。
8. 使用任何缩写编号时，文档中必须有读者可见的“编号说明”，解释字母代表的类别和编号用途；不得让 `C-01`、`H-09` 等代码无说明地首次出现。编号规范见 [evidence-and-claims.md](references/evidence-and-claims.md)。

## 上会评审稿与阶段推进

文档统一用于上会评审，不按工作底稿、对外成稿另设多份版本。PR 与 FAQ 仍为两个独立交付物，台账用于追溯。材料就绪与项目获批分别记录。

1. 材料可以带关键未知和阻断项上会，用于讨论是否验证、调整或停止。必须说明未知对本次决策的影响、补证方式和建议；负责人或期限尚无依据时写“拟请会议确定”，不得编造。
2. 在主评审文档开头说明本次评审目的、建议结论、请会议决定的事项、关键依据和主要风险；资源投入与备选方案按议题需要提供。同一次会议只设一处完整摘要，配套文件引用该摘要，不重复生成汇总文件。PR 与 FAQ 配套时通常在 FAQ 开头承载摘要。
3. 本技能提出的推进或取舍结论标为“建议”，事实核对与实测结果据实表述；真实裁决另记批准人、日期、范围、条件及依据。本次尚未裁决的事项保持“未评审”，保留历史有效裁决，不预填新的批准记录。
4. 完整交付仅在有权人批准相应范围、该范围的阻断项清零且前置条件满足后推进。有条件通过时只开展裁决明确允许且前置条件已满足的工作；未满足条件的部分暂停。核心价值待验证时，只可按已批准的验证范围开展 PoC，不扩为完整交付。

## 工作路由

按当前任务只读取需要的规范，不要默认加载全部参考文件：

- 想法粗糙、证据不足或需要重新界定客户问题：读 [00-five-questions.md](references/00-five-questions.md)。
- 起草或评审未来新闻稿：读 [01a-pr-press-release.md](references/01a-pr-press-release.md)。
- 起草或评审客户/内部 FAQ、假设或 go/no-go：读 [01b-faq.md](references/01b-faq.md)。
- 将产品定义转为拟议或已批准的范围、非目标和验收指标：读 [01c-prd.md](references/01c-prd.md)。
- 任何成文或评审任务：同时读准确性纪律引用的两份规范。

## 工作流

1. 确认项目目录、任务目标、本次会议目的和已有裁决；先执行输入盘点和适配性检查，已有材料不重复制造，缺资料时先引导补充。
2. 建立或更新产品定义台账。新项目可复制 [product-definition-ledger.md](assets/product-definition-ledger.md)。
3. 用五问形成可辩护的客户、问题、首要收益、证据和目标体验。答不出的项进入验证计划。
4. 写 PR 与 FAQ。谁先写不作硬规定，但必须输出为两个独立文件并互相校验；PR 聚焦客户价值，FAQ 承担细节、经济性、依赖、风险与假设。
5. 完成资格检查并提出 go/no-go 建议，列出待决策事项；实际裁决由用户或用户指定的有权人作出，会后按真实记录回写。
6. 按本次议题编制 PRD 评审内容；范围、非目标、指标和假设必须能回指产品定义及来源，未批准部分标为拟议。用于执行的范围必须满足阶段推进条件。
7. 上会前执行跨文档一致性与可读性检查；将未通过项、冲突与阻断项直接报告，说明它们阻断哪项决策或执行工作。

## 输出约定

1. 正文写入用户指定的项目目录。默认中文 Markdown；命名可沿用 `YYYYMMDD-S1-项目关键字-交付物.md`，但项目已有规范时服从项目规范。
2. 同时产出 PR 与 FAQ 时必须写成两个文件，例如 `YYYYMMDD-S1-项目关键字-PR.md` 和 `YYYYMMDD-S1-项目关键字-FAQ.md`；不得合并成一个 PRFAQ 文件。客户 FAQ 与内部 FAQ 可同处 FAQ 文件的两个章节。
3. 文档使用编号时，在目录之后或编号首次出现前设置“编号说明”。只列本文件实际使用的类别，并说明编号用于跨文档追溯；沿用项目既有编号体系时同样要解释。
4. 原始材料只进不改；引用会议或访谈时保留原说话人标识、时间戳和来源文件，不推断身份归属。
5. 不要求 PR 达到固定页数。以“完整表达核心客户价值且没有可删除内容”为准；篇幅过长通常提示主线不聚焦，但不能为压页删除必要事实、边界或风险。
6. 旧水电范例不作为默认模板，也不自动读取。任何历史范例都只能参考结构和节奏，禁止复用其中事实、数字、客户引语和产品结论。
7. 正文之外另给简短自检结果：已验证、仍待验证、阻断项、跨文档冲突、输入适配性问题、建议裁决。

## 完成标准

- 客户、问题、首要收益和目标体验一致，并有对应证据或明确假设状态。
- PR 中每项承诺都能在 FAQ/台账中找到支撑、假设或风险说明。
- FAQ 覆盖客户问题和内部问题；关键未知没有被伪装成确定答案。
- PRD 的范围、非目标和指标来自有来源的产品定义，拟议与已批准状态清楚。
- go/no-go 建议及待决策事项明确；已有裁决按真实记录留痕，未开会不妨碍评审材料完成。
- 跨文档一致性检查通过，或未通过项已明确阻断交接。
- 所有编号均有读者可见的类别说明；PR 与 FAQ 为两个独立文件。
- 缺失资料和输入冲突已被明确提示，没有用虚构内容填补。
