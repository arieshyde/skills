# Business+FDE 产品发现

版本：1.2.0（2026-09-29）。本目录的参考规范随本技能整体版本管理，与产品交付技能 1.2.0 配套。

## 目的与边界

- 定位：Business+FDE 角色采用 Amazon/AWS Working Backwards（客户倒推机制）推进项目的工作方案；产品定义阶段的全部交付物围绕 Working Backwards 产出。
- 核心产物：五问、未来新闻稿（PR）、客户与内部 FAQ、PRD。原型及后续研发交付由 `business-fde-product-delivery` 承接。
- 内容分两层，须分开表述：五问、未来 PR、FAQ 和“以客户价值检验假设”属于 Working Backwards 核心；PRD、文件命名、评审门槛和角色分工是团队落地约定，不应称为 AWS 硬标准。
- 本技能只负责起草、核对、维护文档和准备评审材料。客户触达、承诺、裁决、签字、发送和放行由用户或用户指定的业务负责人执行。本技能不代替用户作批准决定；信息不足时也不代替用户补写结论。

## 硬规则

全程生效。本文件其他章节只引用编号，不重复表述；规则细节由参考规范展开，同一规则不得出现两种表述。

- **H1 不得编造。** 不得虚构客户、场景、痛点、数字、引语、竞品结论或内部决定来补齐正文。负责人或期限没有依据时，写“拟请会议确定”。
- **H2 假想引语显式标注。** 假想引语只能基于已明确的产品设想，且逐处标注“假想引语，仅用于检验目标体验”，不得充当证据。不得编造逼真的姓名、企业名或职位为产品制造背书。
- **H3 主张状态。** 每项关键主张必须标注六种状态之一：**已验证事实**、**有据估算**、**待验证假设**、**已批准决策**、**未来目标**、**未知待补**。定义与来源规则见 [evidence-and-claims.md](references/evidence-and-claims.md)。
- **H4 数字纪律。** 没有来源的数字不得写成事实。数字须注明单位、口径、基线、时间窗和适用范围；缺任何一项即标为估算或待验证。
- **H5 编号按需使用。** 新项目默认不建立主张、假设、冲突、裁决或来源的编号体系。项目已有稳定的编号体系，或编号确实有助于需求、任务、测试管理时可以沿用；不得为了满足模板要求而新增编号，也不得让编号成为理解正文的前提。
- **H6 PR 与 FAQ 为两个文件。** PR 与 FAQ 必须输出为两个独立文件并互相校验，不得合并成一个 PRFAQ 文件。客户 FAQ 与内部 FAQ 可以作为同一 FAQ 文件的两个章节。
- **H7 原始材料与来源展示。** 原始会议记录、访谈转写和客户材料保持原貌，不得改动其中的说话人标注、时间戳，也不得调整内容在文档内的原有位置。派生的 PR、FAQ、PRD、纪要和汇报默认只在文末集中列出主要来源文件，不逐项标注页码、行号和发言时间点。三种情况除外：用户明确要求、直接引用合同或法规原文、处理来源争议。
- **H8 历史范例仅供参考。** 项目目录中既有的历史范例不作为默认模板，也不自动读取。参考历史范例时只借鉴结构和行文节奏，禁止复用其中的事实、数字、客户引语和产品结论。
- **H9 冲突并列记录。** 发现来源冲突时，并列记录冲突双方、影响和待裁决人，不得擅自采信其中一方。

## 输入盘点与适配检查

开始成文前执行：

1. 盘点用户输入和项目已有材料，区分“已有事实”“用户本轮补充”“仍缺资料”三类。不得把文件夹名称、历史范例或常识扩写成项目事实。
2. 项目目录没有内容或材料不足时，先说明当前能做什么、缺什么，再引导用户提供最小资料：项目目标或触发背景、目标客户/用户、已观察到的问题、原始证据位置、现有方案、约束与已有裁决。每轮优先问对方向影响最大的问题；也可以给出一份便于填写的缺口清单。
3. 缺关键资料时，先提供资料清单、访谈提纲或待验证问题。已有信息足以明确本次议题时，可形成上会稿，供会议讨论是验证、调整还是停止。正文遵守 H1。
4. 用户输入与项目名称、已有产品定义、术语表、阶段目标或证据明显不符时：先指出具体冲突及其影响，请用户确认这是新方向、误贴内容，还是需要修改原项目定义。确认前不得把冲突内容扩写为正式产物。
5. 用词疑似有误、有歧义、夸大，或把假设说成事实时：引用原词，说明问题，给出一至两个候选改法。影响产品含义的词必须经用户确认后再使用；不影响含义的明显笔误可直接修正，但须简要说明改动。

## 准确性要求

1. 分清客户、实际用户、付款人和受影响者，不默认四者相同。
2. 客户需求只能由客户原话、行为、现场观察或客户数据支持。市场、法规和技术资料可补充背景，不能冒充客户证据。
3. PR、FAQ、PRD 必须使用同一套产品定义、术语、指标、范围、假设及其验证状态，并按 [review-and-consistency.md](references/review-and-consistency.md) 校验。
4. 主张状态、数字、引语、编号与冲突处理按 H1–H5、H9 执行。

## 评审与阶段推进

所有文档统一用于上会评审，不得以工作底稿或对外成稿为名另设多份版本。“材料就绪”与“项目获批”是两回事，须分别记录。

1. 材料可以带着关键未知和阻断项上会，供会议讨论下一步是验证、调整还是停止。须说明未知项对本次决策的影响、补证方式和建议。
2. 主评审文档开头写明：本次评审目的、建议结论、请会议决定的事项、关键依据和主要风险。资源投入与备选方案按议题需要提供。
3. 同一次会议只设一处完整摘要，配套文件引用该摘要，不重复生成汇总文件。PR 与 FAQ 配套时，摘要通常放在 FAQ 开头。
4. 本技能提出的推进或取舍结论一律标为“建议结论”；事实核对与实测结果据实表述。会议真实作出的裁决，另行记录批准人、日期、范围、条件及依据。本次会议未裁决的事项保持“未评审”状态；历史上仍然有效的裁决予以保留，不预填新的批准记录。
5. 完整交付须同时满足三个条件：业务负责人批准相应范围、该范围内阻断项清零、前置条件满足。有条件通过时，只开展裁决明确允许且前置条件已满足的工作，未满足部分暂停。核心价值待验证时，只按已批准的验证范围开展 PoC，不得扩大为完整交付。

## 工作路由

按当前任务只读取需要的规范，不默认加载全部参考文件：

- 想法仍粗糙、证据不足或需要重新界定客户问题：读 [00-five-questions.md](references/00-five-questions.md)。
- 起草或评审未来新闻稿：读 [01a-pr-press-release.md](references/01a-pr-press-release.md)。
- 起草或评审客户/内部 FAQ、假设或 go/no-go：读 [01b-faq.md](references/01b-faq.md)。
- 将产品定义转为拟议或已批准的范围、非目标和验收指标，或对项目仓库中的既有 PRD 先评审、再修改更新（升版）：读 [01c-prd.md](references/01c-prd.md)。
- 任何成文或评审任务：同时读 [evidence-and-claims.md](references/evidence-and-claims.md) 和 [review-and-consistency.md](references/review-and-consistency.md)。

## 工作流

1. 确认项目目录、任务目标、本次会议目的和已有裁决。先完成上述输入盘点和适配检查：已有材料不重复产出，缺资料时先引导补充。
2. 在 FAQ 或 PRD 中维护本次议题所需的客户、问题、收益、范围、假设、风险和裁决信息，不另建产品定义台账。
3. 用五问得出关于客户、问题、首要收益、证据和目标体验的结论，结论须有依据、经得起追问。回答不出的条目列入验证计划。
4. 撰写 PR 与 FAQ。先后顺序不作硬性规定，但必须按 H6 输出为两个文件并互相校验。PR 聚焦客户价值；FAQ 承担细节、经济性、依赖、风险与假设。
5. 完成资格检查，提出 go/no-go 建议结论，列出待决策事项。实际裁决由用户或用户指定的业务负责人作出，会后按真实记录回写。
6. 按本次议题编制 PRD 评审内容。范围、非目标、指标和假设必须来自已确认的产品定义或可追溯的来源；未批准部分标为拟议。用于执行的范围须满足「评审与阶段推进」第 5 条。
7. 上会前执行跨文档一致性与可读性检查。未通过项、冲突与阻断项直接报告，并说明各自阻断哪项决策或执行工作。

## 输出约定

1. 正文写入用户指定的项目目录，默认中文 Markdown。命名可沿用 `YYYYMMDD-S1-项目关键字-交付物.md`；项目已有命名规范时服从项目规范。
2. 同时产出 PR 与 FAQ 时的命名示例：`YYYYMMDD-S1-项目关键字-PR.md`、`YYYYMMDD-S1-项目关键字-FAQ.md`（文件分离要求见 H6）。
3. PR 不要求固定页数，以“完整表达核心客户价值且没有可删除内容”为准。篇幅过长时检查主线是否聚焦；不得为了压缩篇幅删除必要事实、边界或风险。
4. 正文之外另附简短自检结果：已验证、仍待验证、阻断项、跨文档冲突、输入适配性问题、建议结论。
5. PR、FAQ、PRD、纪要和项目汇报的主要来源，默认在文末集中列出文件名或链接；同一来源不在表格和段落中反复标注。来源明确且无需单列时可省略来源章节。外部研究的关键数据和判断仍应附可访问链接。

## 完成标准

交付前逐项核对；方括号内为规则出处：

- [ ] 客户、问题、首要收益和目标体验口径一致，各有对应证据或明确的假设状态 [H3]
- [ ] PR 中每项承诺都能在 FAQ 中找到支撑、假设或风险说明 [H3]
- [ ] FAQ 覆盖客户问题和内部问题；关键未知没有被包装成确定答案 [H1]
- [ ] PRD 的范围、非目标和指标来自有出处的产品定义，拟议与已批准状态清楚 [H3/H4]
- [ ] go/no-go 建议结论及待决策事项明确；已有裁决按真实记录留痕；尚未开会不影响评审材料完成
- [ ] 跨文档一致性检查通过，或未通过项已明确标注并说明其阻断的交接环节
- [ ] PR 与 FAQ 为两个独立文件；没有为了满足模板要求而建立编号或追溯体系 [H5/H6]
- [ ] 正文没有不必要的页码、行号、发言时间点或重复来源说明 [H7]
- [ ] 缺失资料和输入冲突已明确提示，没有用虚构内容填补 [H1]

## 补充调研与参数建议

用户要求为产品体验参数（时长、阈值、配比、并发量等）给出建议值，或整理补充调研文档时，按以下步骤执行：

1. 给出建议值前，先检索项目仓库现有素材：用术语关键词（阈值、静音、超时、时长、中断等）检索 01-requirements 各目录，确认既有设计基线、已定案参数和现网反馈，然后再检索外部文献。
2. 外部来源逐条抓取原文核对，不凭搜索摘要采信。仅见于转载的数据，须有两个独立来源或不同研究交叉佐证后方可写入，并在文档中标注核验路径。
3. 既有基线与行业默认值冲突时，以本场景的错误代价为准取舍，写明行业默认值的标定场景和不适用原因，不得直接套用行业默认值。
4. 交付物中显式标注结论修正：原建议、现结论、修正原因。每个建议值附允许范围与上线后验证指标。
