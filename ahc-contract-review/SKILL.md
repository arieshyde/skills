# 合同协议审核 Skill

## 一、启动条件与必填信息

主人指定合同文件路径 + 文件名后启动（Windows 路径按 `X:\xxx` → `/mnt/x/xxx` 转换，不询问不猜测）。

**开始前必须确认的信息：**

1. **我方是谁（必填）**：甲方还是乙方、具体公司主体。主人未说明时**必须提问确认**，禁止默认立场开始审核。
2. **谈判地位（默认"均势"）**：强势 / 均势 / 弱势。不主动提问，主人声明时采用。
   - 强势：可大范围争取权利条款，但注意显失公平导致条款被撤销的风险。
   - 均势：以权利义务对等、增强可操作性为原则。
   - 弱势：底线问题必须修改，非底线问题转为风险提示 + 替代方案。
3. **文本来源（审核中自行判断）**：对方起草的从严审；我方起草的侧重查漏补缺。
4. **背景信息（不阻塞）**：交易目的、是否已履行、在谈争议。不问，但审核发现的疑点列入报告。
5. **文件改名要求**：主人要求修改合同文件名称时直接执行（可逆操作，事后告知新旧名），审核意见 MD 按改名后的文件名命名。

## 二、文件读取

- `.docx` → python-docx 直接读取
- `.doc` → `soffice --headless --convert-to docx` 转换后读取（已验证保真）
- `.pdf` → pdftotext（纯文字）/ rapidocr（扫描版）
- **长合同**：分段完整通读后再汇总，禁止只审开头部分
- **多份关联文件**（如框架协议 + 订单）：支持一次审核多文件，交叉检查一致性

**带修订痕迹/批注的文件（重点）：**

1. 先检测 `word/document.xml` 中 `w:ins` / `w:del` 数量、是否存在 `word/comments.xml`
2. 用 lxml 提取修订明细：插入内容标【增:...】、删除内容标【删:...】，连同所在段落上下文输出
3. 审核基于「接受全部修订后」的最终文本；修订插入的文字若残缺、不成句（如删词后残留半句），必须单独指出
4. 批注意图纳入审核依据
5. **复审主人手动修改后的文件**：提取修订痕迹，逐条列出「已采纳的审核意见」与「未采纳/未处理的意见」，并提醒剩余风险；禁止当作全新文件重新审一遍了事

## 三、数字与算术核验（每次必做）

逐项核验并留存计算过程，任何一项不符即列入必改错误：

1. 表格每一行：单价 × 数量 = 合计
2. 分项合计之和 = 小计 = 合同总价
3. 金额大小写一致（注意「千/仟」「零」等规范写法）
4. 税率约定与含税/不含税表述一致；付款金额、发票金额、违约金计算基数互相吻合
5. 单位统一且合理（套/台/个、人月/人天、‰/%）
6. 日期一致：签订日期、生效日期、各履行期限、质保期起算点之间无矛盾
7. 条款编号连续无跳号，「见第 X 条」等指代真实存在

## 四、三层审查维度

### 第 1 层：文字与形式审查

- 错别字、用词不当、语句歧义、语法错误、删改残留的病句
- 前后一致性：当事人称谓统一、术语定义前后统一、金额大小写一致
- 空白未填项、签署栏完整性、附件清单与实际附件是否一致
- 合同名称与法律性质是否匹配（如名为"委托加工"实为购销）
- 标的物表述与实际清单是否一致（如名为"通信设备"实为水文监测设备）

### 第 2 层：结构与要素审查

对照合同性质检查必备要素是否缺失，并通读全文排查隐藏陷阱（前后矛盾、隐蔽的权利义务不对等）。

**通用必备要素**：主体信息、标的、数量、质量/技术标准、价款/报酬、履行期限/地点/方式、验收、违约责任、争议解决、生效条款。

**按合同类型补充要素清单：**

- 购销/采购：交付与运输、风险转移时点、验收标准与期限、质保期与故障率、付款节点与发票、包装、安装调试与技术支持责任
- 委托开发/技术开发：需求与范围定义、里程碑与交付物、验收标准、知识产权归属（含背景 IP 与成果 IP）、源代码托管/交付、保密、人员投入承诺
- 服务合同：服务范围与 SLA、人员资质、服务考核与扣款、数据安全、退出与交接
- 框架协议：框架协议与订单的优先级、价格机制、最小采购量、自动续约条款、框架协议下单订单的签署流程

### 第 3 层：实质风险审查（我方立场）

固定高风险清单（逐项排查）：

- **付款条款**：预付款比例是否过低、是否存在"未见货先付全款"的零质量杠杆安排、发票开具节点与税率约定、长回款周期与承兑汇票支付（计算实际回款周期）
- **违约责任**：违约金是否过低（威慑不足）或过高（被法院调减风险）、赔偿上限陷阱（尤其"以合同金额/已获报酬为限"类）、**双方违约金是否严重不对等（计算倍数差距）**
- **验收条款**：验收标准是否明确可执行、验收期起算点、默示验收条款（逾期未提异议视为验收）、检验期是否短于安装调试所需时间
- **质保条款**：质保期起算点（发货/验收/投入使用/**挂钩"最终客户"或第三方验收导致无限敞口**）、故障率约定、隐蔽缺陷处理、维修往返费用承担、响应时限
- **交付义务**：是否存在无硬性供货/交付截止日期的安排（如"具体以书面通知为准"）
- **免费义务**：免费维护/升级/开发义务是否无上限、边界是否可客观判定
- **知识产权**：保护范围是否覆盖硬件/结构/PCB 设计（不止软件）、成果归属、侵权责任承担
- **保密条款**：单向还是双向、保密期限、违约责任是否对等
- **争议管辖**：管辖地对我方是否有利（结合主要义务履行方判断）、仲裁还是诉讼
- **终止与解除**：解除后已付款/已交付的处理、对方违约导致解除时我方付款义务是否仍被锁定
- **期限与续约**：无限次自动续约、退出机制、通知期限
- **责任不对等**：只约束我方的单方义务条款、对方免责条款

## 五、输出格式（摘抄式）

### 报告结构

1. **头部**：合同名称、甲方、乙方、标的物/交易内容、合同金额（含核验结论）、审核立场（我方身份）、审核日期
2. **分级意见**，按 ❗ 必改错误 🔴 重大风险 🟡 一般风险 🟢 提示事项 排列：
   - ❗ **必改错误（排在最前，优先于一切风险项）**：
     - 错误的字、词语、句子（错别字、用词不当、病句、删改残留的残缺句）
     - 数字、单位、计算错误（算术不符、大小写不一致、税率/含税矛盾、单位缺失或错误）
     - 条款编号跳号缺号、指代错误、关键日期矛盾
   - 🔴 重大风险：不修改不宜签约
   - 🟡 一般风险：建议修改，可作谈判筹码
   - 🟢 提示事项：可优化，不影响签约大局
3. **每条意见四要素**：
   - 位置与摘要：第 X 条 / 章节号 + 一句话摘要
   - 原文摘抄：引用块完整摘录待修改原文（必须与原文逐字一致）
   - 修改示例：建议条款全文，改动处加粗标注
   - 修改原因：风险分析与法律依据
4. **审核汇总**：全部问题的一句话索引
5. **整体签约建议**：建议签 / 修改后签 / 不建议签 + 理由；区分"必须争取的底线条款"与"可让步的谈判筹码"

### 格式规范

- 正文用列表和键值对，不用箭头符号（→、←）描述顺序，改用编号列表或文字叙述
- 全程中文，不夹杂英文
- 表格仅用于数据对比类内容（如汇总索引），列表能表达的不用表格
- 文件中不写文件路径、不出现真实姓名（当事人用"甲方""乙方"或公司简称）

## 六、输出文件

- 保存位置：被审核文件同级目录
- 命名：`当前合同文件名-审核意见-YYYYMMDD.md`（去掉扩展名；若文件已改名，按新名）
- **绝不修改原合同文件内容**（改名除外），只输出审核意见 MD
- 回复只告知文件路径，不用 MEDIA 投递

## 七、质量红线（防 AI 幻觉）

- 引用法律条文必须确保条文号与内容准确；拿不准时只描述规则不列条文号，并标注"建议法务核验"
- 不得编造合同中不存在的条款；摘抄必须与原文逐字一致
- 数字核验必须实际计算，禁止目测下结论
- 审核意见定位为决策辅助，报告末尾固定提示：「本审核意见为 AI 辅助分析，重大合同建议法务/律师复核」

## 八、谈判策略输出

- 弱势立场时，对底线条款给出"退而求其次"的替代方案链，用编号或文字叙述表达（示例：首选要求预付款；对方不接受则改谈履约保证金；仍不接受则缩短付款周期并约定严格的延期付款责任）
- 重大修改建议标注"对方可能抗拒"并给备选方案
- 区分必须争取与可让步条款，供谈判使用

## 九、收尾

- 审核完成、主人确认后，关键风险点与谈判结论写入 `memory/YYYY-MM-DD.md`
- 审核中发现的通用风险模式（新类型陷阱条款）补充到本 skill 的高风险清单（通过 skill_workshop 更新）
