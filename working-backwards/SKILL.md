# Working Backwards（逆向工作法）

## 核心理念

先讲清楚**客户体验**，再决定**做什么**，最后才解决**怎么做**。顺序不能反：

- 正向（Forward）：我们有什么技术能力 → 能做出什么功能 → 找用户来用
- 逆向（Backward）：客户体验应该是什么样 → 倒推需要什么技术能力 → 评估现有能力缺口

AI 时代通用能力太强，「该做什么」比「怎么做」更难——模型能力越强，越容易掉进「炫技但用不上」的正向陷阱。客户说「我们要 AI 原生解决方案」时，往往给的是愿景而不是需求，这正是需要倒推具体场景的时刻。写新闻稿比写需求文档更难自欺欺人：说不清楚客户价值，新闻稿是写不出来的。

## 何时使用

仅在以下情况使用本 skill：

- 用户提到 working backwards、逆向工作法、PR/FAQ、倒推客户体验
- 用户明确要求按 Working Backwards 方法启动或推进产品/项目

已在本流程中的项目，按当前步骤继续即可，无需重新触发。

## 8 步产品开发闭环

| 步骤 | 关键产出物 | 交接标准 | 负责团队 |
|---|---|---|---|
| ① PRD | 产品需求文档 | 范围边界清晰（含非目标），客户/业务方确认 | Business+FDE |
| ② Mockup UI | 可点击原型 | 关键交互路径评审通过 | Business+FDE |
| ③ 技术设计 | 技术设计文档 | R&D 确认可行性与平台缺口 | Business+FDE ⇄ R&D |
| ④ 任务拆解 | 任务列表 | 颗粒度到可估时/可分工/可验证 | R&D |
| ⑤ 开发实现 | 代码 + 实施总结 | 任务逐项验证通过 | R&D |
| ⑥ 测试 | 测试报告 | 关键指标达标 / 评估闭环跑通 | R&D |
| ⑦ 发布 | 发布记录 | 客户/用户可访问，功能生效 | 全员 |
| ⑧ 迭代复盘 | 复盘文档 + issue | 问题回写上游文档 | 全员 |

流程不是线性瀑布：允许分模块并行推进，进度可以不同步；复盘可能倒逼回到 Step 1 或 Step 3 修改设计假设。发布不是终点，是下一轮迭代的起点。

## 执行流程

### 1. 判断项目阶段与入口

先确认用户当前处于哪一步、已有哪些产出物，再从对应步骤切入，不要每次都从 Step 1 重来。

- 模糊立项（愿景宏大但缺具体场景）→ 先写独立 PR/FAQ（见 `templates/00-pr-faq.md`），再写 PRD
- 明确需求 → 直接从 PRD 开始

### 2. 按步骤执行，产出对应文档

每一步的详细方法与常见错误见 `references/framework.md`；Amazon 原书公开方法论详解见 `references/amazon-working-backwards.md`。产出物一律使用 `templates/` 下的对应模板：

- `00-pr-faq.md` — 模糊立项时的 PR/FAQ（新闻稿 + 内外部 FAQ）
- `01-prd.md` — 产品需求文档（含范围边界、非目标、需求溯源）
- `02-mockup-ui.md` — 原型设计说明（一次性原型声明）
- `03-tech-design.md` — 技术设计文档（联合交接）
- `04-task-list.md` — 任务列表（活文档）
- `05-implementation-summary.md` — 实施总结（诚实记录原型假设与实际实现的差距）
- `06-test-report.md` — 测试报告（对照 PRD 体验目标）
- `07-release-record.md` — 发布记录
- `08-retrospective.md` — 迭代复盘（回写上游文档）

### 3. 维护活文档纪律（最容易失败的一环）

- 任务列表与 PRD 是**活文档**：状态变化必须回写，并指定专人持续维护，否则文档会与事实脱节
- PRD v1→v2 应随 Mockup / 技术设计的反馈真实回写，不是写完就冻结
- 复盘发现的问题必须回写到 PRD / 技术设计 / wiki，并生成 issue

### 4. 交接节点检查

每个交接节点按上表「交接标准」验收（按模块进行），不达标不进入该模块的下一步。重点检查：

- PRD 是否写清「不做什么」——没有非目标的 PRD 会导致中途范围蔓延
- Mockup 是否标注「一次性原型，请勿用于生产」
- 技术设计是否评估了平台能力缺口——技术设计也是「倒逼平台补能力」的沟通工具
- 体验承诺（如「5–10 分钟」）是否只作内部工程目标，未写进 UI 文案

## 职责分工

- 分工见上表：Business+FDE 负责 Step 1–3，R&D 负责 Step 4–6（Step 3 为联合交接），全员参与 Step 7–8
- FDE 离客户最近、又懂技术，天然适合主导「逆向咨询」
- 管理者带头遵守流程，检查每个交接节点是否达标
