# Working Backwards（逆向工作法）

## 核心理念

先讲清楚**客户体验**，再决定**做什么**，最后才解决**怎么做**。顺序不能反：

- 正向（Forward）：我们有什么技术能力 → 能做出什么功能 → 找用户来用
- 逆向（Backward）：客户体验应该是什么样 → 倒推需要什么技术能力 → 评估现有能力缺口

本 skill 中的「客户」是需求方的统称：客户项目指外部客户及其业务方，内部产品指内部需求提出者或立项人；「客户体验」在内部产品场景即内部用户体验。两类场景共用同一套 8 步流程。

AI 时代通用能力太强，「该做什么」比「怎么做」更难——模型能力越强，越容易掉进「炫技但用不上」的正向陷阱。需求方说「我们要 AI 原生解决方案」时，往往给的是愿景而不是需求，这正是需要倒推具体场景的时刻。写新闻稿比写需求文档更难自欺欺人：说不清楚客户价值，新闻稿是写不出来的。

## 何时使用

仅在以下情况使用本 skill：

- 用户提到 working backwards、逆向工作法、PR/FAQ、倒推客户体验
- 用户明确要求按 Working Backwards 方法启动或推进产品/项目

已在本流程中的项目，按当前步骤继续即可，无需重新触发。

## 8 步产品开发闭环

| 步骤 | 关键产出物 | 交接标准 | 负责团队 |
|---|---|---|---|
| ① 产品定义与需求规格化 | PRD、需求规格说明书、项目系统功能清单 | 产品目标与范围经确认；原型覆盖范围的流程、规则、功能及验收判据足够明确 | Business+FDE、需求工程师 |
| ② 原型设计与评审（UI/服务） | 原型及评审记录；无界面项目为服务原型；硬件按形态确定 | 关键路径或服务契约经需求方评审通过，反馈回写需求规格与功能清单 | Business+FDE、需求工程师，R&D 参与 |
| ③ 技术设计与项目规划 | 技术设计、工作量与成本估算、项目计划、联合评审及确认记录 | 技术可行；范围、资源、成本、进度与风险协调一致，按权限确认交付安排 | 项目经理组织，Business+FDE、需求工程师、架构师、开发人员共同参与 |
| ④ 任务拆解 | 开发任务列表 | 承接已确认方案与计划，颗粒度到可估时/可分工/可验证，关联需求及里程碑 | R&D，项目经理协调 |
| ⑤ 开发实现 | 代码 + 实施总结 | 任务逐项验证通过 | R&D |
| ⑥ 测试 | 测试报告（AI Agent 含 Agent Harness 评估） | 关键指标达标 | R&D |
| ⑦ 发布 | 发布记录（硬件含 EVT/DVT/PVT/MP 门禁） | 需求方/用户可访问，功能生效；硬件阶段门禁通过 | 全员 |
| ⑧ 迭代复盘 | 复盘文档 + issue | 问题回写上游文档 | 全员 |

流程不是线性瀑布：允许分模块并行推进，进度可以不同步；复盘可能倒逼回到 Step 1 或 Step 3 修改设计假设。发布不是终点，是下一轮迭代的起点。

本流程是结合需求工程与项目管理实践对 Working Backwards 的团队化改造，不是 Amazon 原书规定的固定 8 步。PR/FAQ、PRD 明确价值与范围；需求规格及功能清单支撑原型；原型评审后联合开展技术设计、估算和项目规划，再细化开发任务。需求管理与项目协调贯穿全过程。

## 执行流程

### 1. 判断项目类型、阶段与入口

先判断项目类型，再确认用户当前处于哪一步、已有哪些产出物，从对应步骤切入，不要每次都从 Step 1 重来。

项目类型（前三类选一）：
- UI 软件产品（含本地安装软件）：Step 2 默认静态 HTML 原型，本地安装软件可补充 Figma 原型
- 无界面软件服务/模型产品：Step 2 使用服务/模型原型（`templates/02b-service-prototype.md`）
- 硬件研发项目：Step 2 不适用界面原型；Step 7 按 EVT、DVT、PVT、MP 阶段门禁推进（定义见 07 模板）

补充规则：
- AI Agent 项目（可落在 UI 或无界面类别）：Step 6 必须包含 Agent Harness 的 LLM Judge 评估，AI 评分与专家复核结合

入口判断：
- 模糊立项（愿景宏大但缺具体场景）→ 先写独立 PR/FAQ（见 `templates/00-pr-faq.md`），再写 PRD
- 明确需求 → 直接从 PRD 开始

### 2. 按步骤执行，产出对应文档

每一步的详细方法、核心内容要求及交接标准见 `references/framework.md`；执行 Step 1–4 时必须读取对应章节。Amazon 公开方法论见 `references/amazon-working-backwards.md`。产出物以 `templates/` 下的对应模板为基础，按下述裁剪规则使用；落盘目录与文件名按第 5 节「输出与命名」执行：

- `00-pr-faq.md` — 模糊立项时的 PR/FAQ（新闻稿 + 内外部 FAQ）
- `01-prd.md` — 产品需求文档（含范围边界、非目标、需求溯源）
- `01a-requirements-spec.md` — 需求规格说明书（软件项目采用《软件需求规格说明书》）
- `01b-system-function-list.md` — 项目系统功能清单（需求规格的结构化索引）
- `02-mockup-ui.md` — 有界面产品原型说明（默认静态 HTML；本地安装软件可补充 Figma；一次性原型声明）
- `02b-service-prototype.md` — 无界面软件服务/模型产品原型：接口、输入输出、能力与负载、质量与健康指标
- `03-tech-design.md` — 技术设计文档（架构、技术方案、平台缺口与风险）
- `03a-estimation.md` — 工作量与成本估算（含商业测算及条件）
- `03b-project-plan.md` — 项目计划（含交付分期、资源、里程碑、联合评审及授权确认）
- `04-task-list.md` — 任务列表（活文档）
- `05-implementation-summary.md` — 实施总结（诚实记录原型假设与实际实现的差距）
- `06-test-report.md` — 测试报告（对照 PRD 体验目标；AI Agent 含 Agent Harness 评估）
- `07-release-record.md` — 发布记录（软件含回滚预案；硬件含 EVT/DVT/PVT/MP 门禁）
- `08-retrospective.md` — 迭代复盘（回写上游文档）

裁剪时保留核心过程与输出物：需求规格、系统功能清单、原型及评审、技术设计、估算、项目计划及确认记录均须有明确承载位置。小项目可合并为同一文档的独立章节，注明模板与章节的对应关系；不得以文档合并替代需求分析、估算或评审。按完整业务链或模块滚动推进，只要求当前交付范围达到对应交接标准；后续范围记录假设与待明确项。不适用内容说明原因，不编造指标、成本或批准结论。

### 3. 维护活文档纪律（最容易失败的一环）

- PRD、需求规格、功能清单、技术设计、估算、项目计划及任务列表均为**活文档**，指定维护人；需求编号贯通功能、原型、设计、任务和测试，任务关联计划里程碑。
- 原型、技术设计及实施反馈须回写相关材料；经确认的范围、计划和预算作为执行基线，变更先评估对范围、进度、成本、质量的影响，再按权限确认和更新，保留变更记录。
- 复盘问题回写受影响的上游材料，并生成 issue；不得以“活文档”为由无记录地改变已确认承诺。

### 4. 交接节点检查

每个交接节点按上表「交接标准」验收（按模块进行），不达标不进入该模块的下一步。遇到需求方确认、评审或验收节点，尚无有效确认时必须暂停相应范围并请求需求方确认，不得自行判定通过；已有有效确认可引用，不重复请求。重点检查：

- PRD 是否写清「不做什么」——没有非目标的 PRD 会导致中途范围蔓延
- 原型是否有需求规格与系统功能清单作为依据，关键规则与未决事项是否明确；PRD 完成不代表需求工程结束
- Mockup 是否标注「一次性原型，请勿用于生产」
- 技术设计是否评估了平台能力缺口——技术设计也是「倒逼平台补能力」的沟通工具
- 估算是否区分工作量、工期、成本、报价和利润；项目计划是否落实资源与依赖，客户期望日期是否已转化为双方确认的交付安排
- 联合评审是否分别记录需求方确认、技术可行、资源预算及商业授权，不能相互替代；已有有效确认可引用，不重复请求，未获确认不得自行标为通过
- 体验承诺（如「5–10 分钟」）是否只作内部工程目标，未写进 UI 文案

### 5. 输出与命名

输出目录按以下优先级确定：
1. 用户指定的项目目录；项目已有文档目录约定（如 `docs/`）时，遵循该约定
2. 用户选择的目录
3. 用户未指定时，先询问期望输出位置，不擅自决定或创建目录

文件命名格式：`<阶段编号>-<阶段名称>-<项目关键字>-v<版本>.<扩展名>`

- 阶段编号与名称：00 PR/FAQ、01 PRD、01a 需求规格说明书、01b 项目系统功能清单、02 原型设计、02b 服务原型、03 技术设计、03a 工作量与成本估算、03b 项目计划、04 任务列表、05 实施总结、06 测试报告、07 发布记录、08 迭代复盘
- 项目关键字：使用用户提供的项目名或简称，去掉空格、连字符与路径特殊字符
- 版本号：客户有版本规则时按客户规则；未提供时默认 v0.1 起稿，评审通过后 v1.0，小修递增次版本，范围或设计变更升主版本
- 扩展名默认 `.md`；客户要求 Word 或 Excel 时按客户格式导出，文件名主干不变

示例：`01-PRD-项目A-v1.0.md`、`02b-服务原型-项目A-v1.0.md`、`07-发布记录-项目A-v1.0.md`

版本号写入文件名；版本升级时按客户归档规则另存新版本文件或重命名当前文件。活文档纪律适用于当前版本文件，历史版本按客户要求归档。

输出前确认目录、项目关键字、版本规则与文件格式；同一项目后续沿用同一约定，不重复询问。同名文件已存在时先确认覆盖或递增版本，不直接覆盖。本约定适用于生成的项目文档，`templates/` 下的模板文件名保持不变。

## 职责分工

- 项目经理统筹范围、进度、资源、成本与风险，组织联合评审并跟踪计划；可由一人兼任多个角色，但须明确责任与授权范围。
- Business+FDE 负责客户价值、范围与前线约束，区分必须满足和可协商条件，并协调客户确认；需求工程师牵头需求规格化、功能清单和需求变更管理。
- 软件架构师牵头技术设计，开发人员参与方案、工作分解和估算；R&D 负责 Step 4–6。涉及测试、部署、运维及外部依赖时，纳入相应责任人员；全员参与 Step 7–8。
- 资源、预算、商业条件及对外交付承诺由相应授权人确认；技术评审通过不等于预算或客户承诺获批。
- 客户项目中，FDE 离外部客户最近、又懂技术，天然适合主导「逆向咨询」；内部产品由最接近内部需求提出者的人承担对应角色
- 管理者带头遵守流程，检查每个交接节点是否达标
