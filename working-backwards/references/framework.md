# Working Backwards 流程详解

本文件规定阶段之间的衔接与记录职责。写作组织、证据要求、交叉检查及示例见 [成果质量参考](output-quality.md)；模板路径均相对 skill 根目录。8 步为团队流程改造，不代表 Amazon 或某项标准的固定顺序。

## 一、产品定义与需求规格化（Step 1）

Business+FDE 明确客户问题、目标用户、预期体验、本期范围与非目标，形成 PRD。模糊立项先用 PR/FAQ 讨论价值、风险和是否继续；其中的粗估与设想不直接成为执行预算或承诺。

需求工程师据此组织两个核心输出：

- **需求规格说明书**：总体业务、分类与大类概述之后，按子需求说明行为、规则、权限、异常与验收判据；共用数据、接口及非功能要求分类说明。
- **项目系统功能清单**：沿用相同业务分类，概括各项能力、范围和分期，关联需求编号；详细规则以需求规格为准，开发任务另列。

两份文档可配套迭代：先建立需求与功能编号并对应，未形成的引用标为待补，配套形成后双向核对，不因互相引用而陷入等待。功能性需求检查功能覆盖；非功能要求直接关联设计与测试，不强行转换成菜单功能。

交接时，本轮原型涉及的产品目标、范围及关键流程规则须经需求方确认。PRD 完成不代表需求工程结束；影响当前设计的未决事项先澄清，后续模块可继续滚动细化。

## 二、原型设计与评审（Step 2）

输入为对应版本的 PRD、需求规格与功能清单。Business+FDE、需求工程师组织业务代表评审，架构师及开发人员识别实现约束。

- **UI**：提供可点击原型及关键路径、状态、权限和异常说明；页面关联功能编号。
- **服务/模型**：提供调用场景、契约、输入输出示例、异常与权限，以及指标目标和验证计划。已有试验另列实测证据，未实施的标为待验证，不要求生产级性能已经达标才开始技术设计。
- **硬件/混合系统**：按对象表达体验模型、样机或服务交互；有 UI 的部分仍按界面原型评审。

原型标明用途与验证范围，原型通过不能当作生产就绪。UI/服务模板默认为一次性体验或契约原型；不得未经工程化、测试与评审直接用于生产。硬件工程样机是否复用按设计与阶段验证结果决定。

输出包含原型、反馈处理和需求方确认记录。新增规则回写需求规格，功能范围变化回写清单，目标变化回写 PRD。原型可以辅助澄清未决规则，但未经确认的设计不能成为后续正式承诺。

## 三、技术设计、估算与项目规划（Step 3）

项目经理组织需求工程师、Business+FDE、架构师和开发人员，按需纳入测试、部署、运维及外部依赖责任人。三个产出相互迭代，最后联合确认。

### 3.1 技术设计

架构师牵头，将需求与原型转成总体架构和模块设计，再说明数据、接口、部署及非功能实现措施。重要方案写出选择理由、替代方案和代价；评估平台能力缺口与复用、新建或采购安排。

关键技术假设有验证结果或明确的验证工作安排。阻塞当前正式交付承诺的假设尚未解决时，可先安排获授权的技术验证，不将未知可行性标为通过。方案需要改变范围或体验时回到需求确认。

### 3.2 工作量、成本与商业测算

按方案分解到可估算工作包，覆盖当前估算范围内的开发、集成、测试、部署与交付支持；如项目总成本包含需求分析、原型及管理工作，也须计入或明确已发生费用的处理口径。Step 4 再细化近期执行任务。

记录方法、来源、假设、区间及风险预留。人日/人月是工作量，人员技能、可用时段和依赖决定工期，不能简单用人月除以人数承诺日期。

人员成本采用公司成本单价，其他适用资源逐项计算；明确单价已含费用、税费口径和预留，避免重复计入。商业测算区分成本、报价与利润，说明利润率口径；利润要求不能反向压低真实工作量。内部产品保留预算及预期效益，外部报价不适用时无需填空表。

### 3.3 项目计划

Business+FDE 带回客户目标、时间要求及原因，区分硬约束与期望。项目经理结合方案、估算和可用资源组织路线图、近期工作包、里程碑、测试、部署及验收安排。

每项关键依赖明确内容、责任方、需就绪日期及确认状态。客户期望与可行安排有差异时，提出范围、分期、方案、资源或时间选项，由前线协调确认；期望日期不直接成为承诺。

路线图说明版本目标与范围，近期计划细化到工作包，远期保留假设并滚动细化。计划引用功能清单、估算和任务的主记录，不复制维护全部明细。

### 3.4 联合确认

需求与原型确认、技术可行、资源预算批准、适用的商业授权、交付范围与时间确认分别记录。项目计划汇总确认依据，已有评审或授权记录直接引用，不重复组织审批或由作者自行标为通过。

获授权且无阻塞事项的当前范围可进入执行任务细化。不受影响的模块可独立推进；探索性工作与正式交付范围应明确区分。

## 四、任务与实现（Step 4–5）

R&D 将工作包细化为有负责人、工作量、依赖、计划日期和验证方式的任务。业务功能、技术实现及必要工程工作可以一对多或多对一关联。估算或里程碑实质变化回到 Step 3 处理。

任务列表是当前任务状态的主记录。实施总结保留指定版本/提交范围的完成快照、产物位置、开发自检证据、运行方式、已知差距及测试条件，不另建实时进度台账。

“可提交测试”指当前测试范围产物可运行、开发自检完成，不要求项目中未来的系统测试、发布等任务也已完成。测试设计可提前进行，开发和测试按模块迭代。

## 五、测试（Step 6）

测试范围及通过标准来自已确认需求，报告绑定具体软件/模型/硬件版本、环境、数据与执行记录。分别报告通过、不通过、未执行和阻塞；未覆盖内容不能计为通过。

AI Agent 的主观输出与任务质量包含 LLM Judge 评估和专家复核；使用可复现用例和执行轨迹验证工具、编排、上下文及恢复行为。时延、成本、权限、数据一致性等客观指标采用日志、计量或断言，不以模型评分替代。校准不足时先修正评估方法，并重新验证受影响结果。

发布条件是当前发布范围关键指标达标、阻塞缺陷关闭且结论有证据。非阻塞遗留项记录影响、责任及处理安排，不能掩盖关键指标失败。任何必要的范围或判据变更均须有授权、理由及重新验证结果，不允许仅改阈值消除失败。

## 六、发布与交付（Step 7）

项目经理协调发布责任人。软件先记录发布前条件、测试结论、回滚安排及授权，再记录实际执行、访问或调用验证及异常。发布准备完成、发布成功、用户可用与需求方验收分别记录，不能相互替代。

硬件按项目适用的 EVT（工程验证）、DVT（设计验证）、PVT（生产验证）、MP（量产）记录当前阶段及退出标准。各阶段是研发循环的放行点，不是直到开发结束才补签的四个勾选项；后续阶段明确未到达，不伪造全部通过。

通知、验收和外部操作沿用用户及项目已有授权。仅起草记录不能写成已经发布、通知或验收；外部系统的实际动作与文档编写分别确认执行证据。

## 七、效果复盘（Step 8）

以发布后的实际数据与用户反馈对照 PRD 成功指标，说明观察范围、差距、原因依据和待验证假设。数据不足时明确尚不能判断及观察安排，不为完成复盘编造收益。

行动项写明负责人、完成条件及计划时间；需追踪的问题关联现有 issue 或列为待创建，不因模板要求自动向外部系统发消息。确有上游变更时评估影响并按权限回写；暂无问题时据实说明，不强制造出问题或 issue。

## 八、信息主记录与变更

| 信息 | 主记录 | 其他材料如何使用 |
|---|---|---|
| 客户价值、产品目标与产品级边界 | PRD；构思阶段为 PR/FAQ | 摘要并引用适用版本 |
| 业务规则、需求状态及验收判据 | 需求规格 | 原型、设计及测试引用需求编号 |
| 功能编号、版本归属及需求覆盖 | 项目系统功能清单 | 计划引用范围，估算按功能核对 |
| 技术决策与约束 | 技术设计 | 估算、任务、实施引用 |
| 工作量估算与成本计算 | 估算 | 计划引用总量和预算依据 |
| 里程碑、资源、联合确认及执行基线 | 项目计划 | 执行任务关联工作包，确认记录引用原始依据 |
| 当前任务状态 | 任务列表 | 总结引用指定时点的快照 |
| 实测、发布及业务效果事实 | 对应测试、发布及复盘记录 | 保留执行版本与证据，不随计划改变而覆盖历史 |

保留需求→功能→原型/设计→任务→测试的追溯。功能清单集中维护需求与功能映射；需求规格不再维护一份反向明细表。非功能要求可直接关联设计与测试。不存在的材料不创建虚假链接。

变更先确定主记录，再分析范围、进度、成本、质量影响，按权限确认并更新关联材料。文档可合并、角色可兼任，但核心内容与确认责任保留；项目管理贯穿全程。
