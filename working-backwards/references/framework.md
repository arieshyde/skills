# Working Backwards 框架详解

来源：Amazon《Working Backwards》（Colin Bryar & Bill Carr）公开方法论，方法论详解见同目录 `amazon-working-backwards.md`；本文件聚焦 8 步流程的执行方法。

## 一、方法论起源

Working Backwards 是 Amazon 自 2004 年起推行的逆向工作法：不从技术能力出发，而是先写「新闻稿 + 常见问题」（PR/FAQ）倒推产品定义。Kindle、AWS、Prime 都由此而来。

要点：

- PR/FAQ 是可重复的循环，不是写完一次就归档的文档
- 新闻稿驱动：先把「做成什么样」写清楚，再谈技术方案
- 双向验证：客户 FAQ 验证「客户是否买账」，内部干系人 FAQ 验证「内部是否谈得拢」，两者都要过
- 快速迭代：用故事板/技术图示把分歧摆上桌面辩论，再回改新闻稿；小团队 + 单线程负责人（Single-Threaded Leader）保证循环转得快
- Amazon 实践中 PR/FAQ 常需 10 稿以上、与高层 5 次以上评审会；PR 少于一页，FAQ 不超过五页——篇幅限制是强制思考的「forcing function」

### 经典案例（讲给团队听的三个故事）

AWS、Kindle、Prime 三个公开案例详表见同目录 `amazon-working-backwards.md` 第五节。

### 正向 vs 逆向思维

- 正向（Forward）：我们有什么技术能力 → 能做出什么功能 → 找用户来用
- 逆向（Backward）：客户体验应该是什么样 → 倒推需要什么技术能力 → 评估现有能力缺口

AI 时代的陷阱：模型能力太强、太通用，反而更容易掉进「正向」陷阱——做出炫技但用不上的东西。中国客户常见诉求「我们要 AI 原生解决方案」——愿景宏大但缺乏具体场景，这不是客户的问题，而是 AI 通用性带来的必然结果；Working Backwards 正是为此设计。

## 二、PR/FAQ 具体化

### 新闻稿结构（Press Release）

1. 标题——一句话说清产品是什么
2. 副标题——客户获得的核心利益
3. 概述——是什么、给谁用、为什么是现在
4. 问题——客户当前的具体痛点
5. 解决方案——怎么解决、关键能力
6. 客户引语——设想真实客户会怎么称赞它

### 关键问题清单（FAQ）

内部：

- 为什么是现在，不是以后？
- 最大的技术/资源风险是什么？
- 用什么指标判断成功或失败？

外部：

- 客户为什么要换掉现在的方式？
- 定价/获取方式是什么？
- 对客户现有数据/工作流有什么影响？

## 三、8 步流程逐条详解

### Step 1 — 产品需求文档（PRD）｜Business + FDE

- 目的：从客户/用户体验倒推，先讲清楚做什么、给谁用、解决什么问题、**以及不做什么**
- 产出物：PRD 文档（含范围边界、非目标）
- 现状：目前是 PR/FAQ 的简化版；遇到模糊立项可先写独立 PR/FAQ
- 实践要点：PRD 明确写「MVP 不做什么」边界，UI / 技术设计忠实执行，避免中途范围蔓延
- 实践要点：需求可溯源到客户输入（会议原文时间戳/工单/访谈记录），痛点→模块保留可追溯映射

### Step 2 — Mockup UI 原型设计｜Business + FDE

- 目的：用可点击原型验证交互与信息架构，不锁定技术实现
- 产出物：HTML/Figma 原型 + 设计说明文档
- 提醒：明确标注「一次性原型，请勿用于生产」（THROWAWAY PROTOTYPE），避免原型代码顺手变成生产代码
- 实践要点：Mockup 明确标注 THROWAWAY PROTOTYPE，客户评审记录逐条留痕

### Step 3 — 技术设计文档｜联合交接（Business+FDE ⇄ R&D）

- 目的：把已经验证过的客户体验转译为可行技术方案，评估平台能力缺口
- 产出物：技术设计文档
- 定位：Step 3 是 Business+FDE 与 R&D 的**联合交接点**，不是任何一方单独拥有
- 提醒：技术设计也是「倒逼平台补能力」的沟通工具，不只是「我们怎么做」

### Step 4 — 任务拆解｜R&D

- 目的：把技术设计拆成可执行、可估时、可分工的任务清单
- 产出物：任务列表文档
- 提醒：任务列表是「活文档」，必须有人持续回写更新，否则会变成「入职时准确、上线时过时」的文件
- 常见失败模式：任务列表文档（04-task-list.md）本身没有被回写，进度记录悄悄搬到了实施总结/复盘文档里——活文档需要专人持续维护

### Step 5 — 开发实现｜R&D

- 目的：按任务清单执行开发
- 产出物：代码 + 实施总结文档
- 提醒：诚实记录 mock vs 真实的差距，比一次性宣称「完成」更有价值

### Step 6 — 测试｜R&D

- 目的：验证功能是否真正达到**客户体验目标**，不只是「跑通」
- 产出物：测试报告 / 评估结果
- 提醒：可引入 LLM Judge 等离线评估闭环，量化「排序质量」「回答质量」等主观指标

### Step 7 — 发布｜全员

- 目的：把验证过的方案交付给客户 / 用户
- 产出物：发布记录
- 提醒：发布不是终点，是下一轮「迭代与复盘」的起点

### Step 8 — 迭代与复盘｜全员

- 目的：检验真实效果、发现问题、回写上游文档（PRD / 技术设计 / wiki）
- 产出物：复盘文档 + issue 记录
- 提醒：复盘可能倒逼回 Step 1/3 的设计假设——不是走个形式的总结会
- 实践要点：复盘要能真抓到产品缺陷，当场修复并回写上游

## 四、落地行动要求

- 把 8 步流程定为团队**默认工作方式**——不是建议，是标准
- 「先讲清楚客户体验，再决定做什么」成为默认动作，而不是「技术能做什么就做什么」
- 管理者带头遵守，检查每个交接节点是否达标，不放任自流
