# Working Backwards 框架详解

本框架以 Amazon Working Backwards 的客户价值导向为起点，结合需求工程与项目管理实践形成团队执行规范。8 步划分及模板组合是本 skill 的改造，不是 Amazon 或某项标准规定的固定流程。Amazon 公开方法论见 `amazon-working-backwards.md`。

> 本文中的「客户」统称需求方：客户项目指外部客户及其业务方，内部产品指内部需求提出者或立项人；两类场景共用同一套 8 步流程。
>
> 软件项目按下述需求规格化要求执行；软硬件混合项目区分系统需求与软件需求，纯硬件项目按对象调整需求规格及功能清单，保留核心过程与输出。其他类型适配：UI 软件使用静态 HTML 原型（本地安装可补充 Figma）；无界面服务/模型使用服务原型（`templates/02b-service-prototype.md`）；硬件项目 Step 7 按 EVT、DVT、PVT、MP 门禁。8 步流程本身不变。
>
> 产出物的目录与文件名遵循 SKILL.md 执行流程第 5 节「输出与命名」。
>
> 遇到需求方确认、评审或验收节点，尚无有效确认时暂停相应范围并请求确认，不得自行判定通过；已有有效确认可引用。

## 一、方法论起源

Working Backwards 是 Amazon 自 2004 年起推行的逆向工作法：不从技术能力出发，而是先写「新闻稿 + 常见问题」（PR/FAQ）倒推产品定义。

要点：

- PR/FAQ 是可重复的循环，不是写完一次就归档的文档
- 新闻稿驱动：先把「做成什么样」写清楚，再谈技术方案
- 双向验证：客户 FAQ 验证「客户是否买账」，内部干系人 FAQ 验证「内部是否谈得拢」，两者都要过
- 快速迭代：用故事板/技术图示把分歧摆上桌面辩论，再回改新闻稿；小团队 + 单线程负责人（Single-Threaded Leader）保证循环转得快

### 经典案例

AWS、Kindle、Prime 三个公开案例的详表见同目录 `amazon-working-backwards.md` 第六节。

## 二、8 步流程逐条详解

### Step 1 — 产品定义与需求规格化｜Business+FDE、需求工程师

PR/FAQ 表达客户价值和预期体验，PRD 明确产品目标、目标用户、本期范围、非目标及成功标准。模糊立项先写 PR/FAQ；明确需求可从 PRD 切入。PRD 经确认表示产品层面的目标与范围明确，不能视为需求工程结束，也不把 PRD 等同于 PR/FAQ 的简化版。

需求工程师牵头，Business+FDE 配合，将产品要求细化为两个核心输出：

- **需求规格说明书**（`templates/01a-requirements-spec.md`）：软件项目采用《软件需求规格说明书》，明确角色、流程、功能行为、输入输出、业务规则、权限、状态、异常、外部接口、性能、安全、可靠性等非功能要求，以及可验证的验收判据。按需求编号关联 PRD、来源和功能编号；区分已确认要求、假设和待确认项，不擅自补齐业务规则。
- **项目系统功能清单**（`templates/01b-system-function-list.md`）：统一名称，列出模块、功能编号、功能说明、对应需求、优先级、所属版本、本期是否包含、依赖与确认状态。它是需求规格的结构化索引，描述系统能力，不替代开发任务列表。

交接：产品目标与范围经需求方确认；本轮原型覆盖范围内的关键流程、规则、数据、权限、功能及验收判据足够明确。影响设计的未决事项有责任人及处理安排；阻塞事项解决前，不得将其作为已确认设计依据。按完整业务链或模块滚动细化，无须等待全系统一次性定稿。

### Step 2 — 原型设计与评审（UI/服务）｜Business+FDE、需求工程师

输入为已确认的 PRD、需求规格说明书和项目系统功能清单，注明适用版本与覆盖范围。

- UI 软件：可点击静态 HTML 原型及设计说明；本地安装软件可补充 Figma。
- 无界面服务/模型：服务契约、输入输出样例和交互流程原型（`templates/02b-service-prototype.md`）。
- 硬件按产品形态表达关键体验；不强制界面原型。

原型关联需求及功能编号，呈现主路径、关键异常、状态变化和权限差异；声明一次性原型，不代表生产实现。业务代表验证能否完成任务，需求工程师检查规则与覆盖，架构师和开发人员参与识别实现约束。发现业务规则缺失时先澄清，不由原型作者自行定义。

输出为原型及评审记录，逐条记录反馈、处理结果、受影响文档和需求方确认。反馈回写需求规格、功能清单，影响价值与范围时回写 PRD；经确认后作为 Step 3 的共同输入。

### Step 3 — 技术设计与项目规划｜项目经理组织，多角色联合评审

项目经理组织需求工程师、Business+FDE、软件架构师、开发人员共同讨论；按需纳入测试、部署、运维及外部依赖责任人员。技术设计、估算和计划相互迭代，不能仅凭前线日期形成开发承诺。

#### 3.1 技术设计

架构师牵头，开发人员参与，基于需求规格、功能清单及评审后的原型确定架构、技术选型、模块划分、数据与接口、复用/新建/采购、部署条件、非功能实现措施及技术风险。评估平台能力缺口，明确补齐责任与依赖；必要时先验证关键技术假设。

输出：**技术设计文档**（`templates/03-tech-design.md`），关联需求与功能编号，记录备选方案、取舍依据、风险与待验证事项。技术评估可提出范围或体验调整，须回到需求和原型确认，不能由研发单方面更改客户承诺。

#### 3.2 工作量、成本与商业测算

研发依据技术方案进行支撑估算所需的工作分解，覆盖开发、集成、测试、部署及适用的交付支持；Step 4 再细化到具体可执行任务。记录估算方法、假设、数据依据、区间/不确定性及风险预留，缺少公司成本参数时保留待填项，不编造数字。

- 人日/人月表示工作量；人员可用性、任务依赖及并行条件共同决定工期，不能机械地用人月除人数确定交付日期。
- 按公司人月成本口径及第三方服务、软件许可、设备、环境、差旅等适用投入计算成本，注明已包含的费用，避免重复计入。
- 商业测算结合成本、税费口径、利润要求和市场条件形成报价或承接建议。区分成本单价与对外报价单价、毛利率与成本加成率，不以利润目标反向压低真实工作量。
- 内部产品保留工作量、成本、预算及预期效益分析；不适用的对外报价和利润测算说明原因。

输出：**工作量与成本估算**（`templates/03a-estimation.md`），商业敏感数据按读者权限放置在内部部分或独立附件，对外引用经批准口径。

#### 3.3 项目计划与交付安排

Business+FDE 提供客户时间要求、业务目标及原因，区分硬约束、期望和可协商条件。项目经理结合研发估算、真实资源及依赖，组织确定首期范围、交付分期/路线图、人员安排、开发顺序、测试部署验收活动和里程碑。路线图表达版本目标与范围，近期执行计划细化到可跟踪工作包，远期保留假设并滚动细化。

外部依赖写明交付内容、责任方、需就绪日期及其确认状态。客户期望与可行安排冲突时，提出范围、分期、方案、资源或时间调整选项，Business+FDE 协调客户确认；不得把期望日期直接写成已承诺日期。

输出：**项目计划**（`templates/03b-project-plan.md`），包含范围、资源、里程碑、责任、预算关联、质量与验收安排、风险、沟通跟踪节奏及变更方式。

#### 3.4 联合评审与授权确认

评审分别记录需求与原型确认、技术可行性、资源与预算批准、适用的商业审批、客户交付范围与时间确认。各项由有权人员确认，技术评审不能代替预算批准，内部估算不能代替对外承诺。已有有效确认可引用；缺少确认时明确状态，不能自行判为通过。

输出：**联合评审及确认记录**，默认放入项目计划，也可引用现有评审记录。记录材料版本、结论、授权人、依据、遗留事项及其影响。阻塞事项闭环后，相关范围进入 Step 4；不受影响且已获授权的模块可独立推进。

### Step 4 — 开发任务拆解｜R&D，项目经理协调

承接已确认的技术方案、估算及项目计划，将工作包细化为可估时、可分工、可验证的任务。需求/功能清单描述产品能力，任务列表覆盖实现这些能力所需的开发、集成、测试及部署等工作，允许一对多和多对一关联。

输出：**开发任务列表**（`templates/04-task-list.md`），关联需求、功能、技术设计和里程碑，明确负责人、工作量、计划日期、依赖、验证方式与状态。细化后若估算或里程碑发生实质变化，回到 Step 3 评估并确认，不能悄悄修改计划。

指定维护人，以任务列表跟踪任务进度；项目计划跟踪里程碑和资源，两者相互引用，避免重复维护冲突数据。按当前迭代细化，无须预先拆完所有远期任务。

### Step 5 — 开发实现｜R&D

- 目的：按任务列表执行开发
- 产出物：代码 + 实施总结文档
- 提醒：如实记录差距，不要一次性宣称「完成」

### Step 6 — 测试｜R&D

- 目的：验证功能是否真正达到**客户体验目标**，不只是「跑通」；无界面项目重点验证能力、质量与健康指标
- 产出物：测试报告 / 评估结果；AI Agent 项目附 Agent Harness 的 LLM Judge 评估
- 提醒：AI Agent 的 Agent Harness（工具调用、上下文与记忆、任务编排、错误恢复、护栏）必须纳入 LLM Judge 评估；项目/产品级 Judge 由 AI 评分与专家复核结合。评估口径不准确时，先修正评估集、指标定义或 Judge 配置，再判定结果

### Step 7 — 发布｜全员

- 目的：把验证过的方案交付给需求方 / 用户
- 产出物：发布记录；软件项目附回滚预案，硬件项目附 EVT（工程验证）、DVT（设计验证）、PVT（生产验证）、MP（量产）门禁记录
- 提醒：软件项目确认回滚预案与需求方通知已就绪；硬件项目按 EVT（工程验证）、DVT（设计验证）、PVT（生产验证）、MP（量产）阶段门禁逐级放行，每阶段明确退出标准与回退/改版预案

### Step 8 — 迭代复盘｜全员

- 目的：检验真实效果、发现问题、回写上游文档（PRD、需求规格、功能清单、技术设计、估算、项目计划等）
- 产出物：复盘文档 + issue 记录
- 提醒：复盘可能倒逼回到 Step 1 或 Step 3 的设计假设——不是走个形式的总结会

## 三、落地行动要求

- 把 8 步流程定为团队**默认工作方式**——不是建议，是标准
- 「先讲清楚客户体验，再决定做什么」成为默认动作，而不是「技术能做什么就做什么」
- 管理者带头遵守，检查每个交接节点是否达标，不放任自流

## 四、裁剪与变更管理

- 保留需求规格、系统功能清单、原型及评审、技术设计、估算、项目计划及联合确认这些核心输出；可合并载体、缩减不适用章节，须标明内容位置及不适用原因，不能省略核心过程。
- 多角色可由同一人兼任，须明确项目经理及各项维护责任；审批按实际权限执行，不能用角色兼任推定批准。
- 经确认的范围、进度与预算作为执行基线。变更评估范围、进度、成本、质量影响后按权限确认，并更新受影响的需求、原型、方案、估算、计划、任务及测试；保留版本和变更依据。
- 项目管理贯穿启动、规划、执行、监控及收尾，本 skill 的阶段划分不把这些管理活动限制在 Step 3；早期探索可做粗估，正式交付安排按本节联合规划结果确认。

- [PMI 进度规划实践标准](https://www.pmi.org/-/media/pmi/documents/public/pdf/certifications/practice-standard-scheduling.pdf)：进度模型、资源依赖与计划更新。
