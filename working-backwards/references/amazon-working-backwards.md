# Amazon Working Backwards 公开方法说明

本参考仅解释本 skill 使用的方法来源。依据为作者公开说明和 Amazon 刊登的原书节选，不是全书全文复述，也不代表 Amazon 所有团队的统一实施规定。

## 1. 客户价值与 PR/FAQ

Working Backwards 从期望的客户体验出发，用模拟未来发布的新闻稿和 FAQ 澄清产品价值、解决方式及关键难题。新闻稿使团队聚焦客户能获得什么；FAQ 进一步讨论使用体验、资源、技术、商业及运营条件。[作者说明](https://workingbackwards.com/resources/working-backwards-pr-faq/)

原书公开节选强调多轮讨论与修订，也说明项目启动后 PR/FAQ 仍会变化。少于一页的新闻稿和不超过五页的 FAQ 是保持精炼的写作约束；重点是思考质量，不是页数或修订次数本身。[Amazon 原书节选](https://www.aboutamazon.com/news/workplace/an-insider-look-at-amazons-culture-and-processes)

## 2. 评审与开发衔接

评审通过阅读、质询和讨论改进想法，并逐步形成是否继续投入的决定。作者说明，获准推进时应已经理解资源、粗略时间线与运营事项；之后可以使用敏捷方法开发产品。这不表示每个项目必须再按统一次序生成独立 PRD、原型及技术设计等文档。[作者说明](https://workingbackwards.com/resources/working-backwards-pr-faq/)

本 skill 将早期资源判断视为规划输入，正式范围、预算和交付安排由后续联合规划确认。讨论价值、验证假设与正式执行可以有不同授权范围。

## 3. 指标与持续检验

可控输入指标反映团队能够通过行动改善、并影响客户结果的因素；输出指标反映业务结果。选择输入指标需要验证它与结果的关系，不能把所有活动量或使用量自动视为有效输入。作者以持续业务评审讨论指标及其变化。[作者关于输入指标的说明](https://workingbackwards.com/concepts/input-metrics/)

本 skill 据此要求 PRD 明确成功指标、复盘检查真实效果；软件测试的验收判据与业务结果指标仍分别定义。工程指标通过不能证明业务收益已经实现。

## 4. 本 skill 的团队化改造

PRD、需求规格、系统功能清单、8 个执行阶段及联合交接条件，是本 skill 结合需求工程与项目管理实践的约定。具体要求以 SKILL.md、流程详解与模板为准。

PR/FAQ 支持价值讨论；需求规格与功能清单支持原型和实现；方案、估算及计划支持执行；测试、发布和复盘分别提供质量、交付和实际效果证据。文档数量可裁剪，核心过程与信息仍须保留。
