# 成果质量与交叉检查

本参考适用于全部关键输出。目标是让读者看清当前结论、依据和下一步；模板中的栏目只是提醒，最终内容要体现分析与取舍。

## 1. 按读者的任务组织成果

起草前明确读者、用途、本次范围和已有依据。已有上下文足够时直接采用，不把这一检查变成固定问卷。

| 成果类型 | 开头应让读者知道 | 随后展开 |
|---|---|---|
| PR/FAQ、PRD | 客户问题、价值及本期方向 | 场景、范围、关键假设与待决问题 |
| 需求规格、功能清单 | 整体业务、能力边界与分类 | 各大类概述、子项说明、规则及关联 |
| 原型、技术设计 | 验证什么或建议采用什么方案 | 关键路径、模块、取舍、约束与证据 |
| 估算、计划、任务 | 投入或交付安排及成立条件 | 分解依据、依赖、责任、时间与风险 |
| 实施、测试、发布、复盘 | 当前实际结果及适用范围 | 证据、差距、影响与后续行动 |

需求与功能按“整体概述 → 大类总览 → 大类概述 → 子项说明”展开；结果报告先给结果概述，再展开分类证据，不生搬需求目录。每章先说明主题与范围，同一段围绕一个问题，避免标题下面连续堆叠不同性质的事项。

## 2. 分类、段落与表格

需求规格和功能清单选用一致的主分类与顺序：可按业务场景，也可先按使用者/使用端划分，再在端内细分场景。业务用户端、管理后台是使用视角，不等于代码的前端、后端。需要多个视角时确定主目录，其余用角色或关联信息表达。

大类先说用途与边界，子项再说使用者、行为与结果。正常流程、规则、异常和验收判据分开说明。共用能力或规则只完整定义一次，其他位置引用；编号随内容稳定，不能随章节重排任意变化。

表格用于总览、短参数、版本范围和映射；长流程与规则用正文。宽表包含不同用途时按主题拆开。简单子项可用一个完整段落，不必为一句话创建多层空标题；复杂子项才分多个小节。合并后仍应能辨认范围、行为、边界和验收依据。

## 3. 事实、目标与确认状态

- 事实和结论附适度来源，优先引用现有文件、记录或证据；一般在章节或文末列来源，不强加访谈时间戳。测试、发布等需要定位实际执行的记录保留必要时间与版本。
- 目标注明拟议或已确认状态，实测结果注明环境、数据、方法和产物版本。目标未实测不妨碍需求讨论，但不得写成结果。
- 缺失的成本、日期、指标、规则或审批，不用“合理值”补齐。写清待确认内容、影响、责任角色和处理安排；未知人员姓名或截止日期同样标为待确认。
- PR/FAQ 的发布场景属于设想；设想引语须紧邻注明“模拟”，不虚构真实客户证言。真实引语须有来源。
- 单元测试、模拟原型、本地构建分别支持其验证范围，不能推导出生产可用、客户接受或业务收益已达成。

## 4. 前后交叉检查

起草前读取上游、配套材料及已有反馈，确认版本与范围；提交前按以下顺序检查：

1. **文内检查**：概述、分类、明细和汇总一致；名称、编号、角色、规则、指标、单位与状态无冲突。
2. **向前追溯**：逐项查明来源或获授权的推导依据，未增加未经确认的业务范围。
3. **向后覆盖**：上游当前范围没有遗漏；已有原型、方案、估算、任务或测试的反馈已处理。尚未形成的下游只检查其所需输入是否充分。
4. **同阶段互查**：需求规格与功能清单、技术设计与估算和计划之间范围及假设一致。工作量与成本应重算合计，日期安排应检查依赖和资源。
5. **处理差异**：可修正的直接修正；需业务决定的事项记录影响及处理安排。将简短检查结论放入现有记录或交付说明，不新增独立检查报告，也不把自查写成业务批准。

### 各输出的检查重点

| 关键输出 | 向前核对依据 | 向后检查衔接及已有反馈 |
|---|---|---|
| PR/FAQ、PRD | 客户来源、价值目标、范围和既有决定 | 需求规格能否承接目标与边界；已有原型或方案是否改变客户体验 |
| 需求规格说明书 | PRD 范围、来源和业务约束 | 与功能清单分类、编号和覆盖双向一致；足以支撑原型与验收 |
| 项目系统功能清单 | 需求规格各类功能需求及本期范围 | 原型覆盖与分期、估算范围一致，共用能力无重复计数 |
| 原型及评审记录 | 需求规格、功能清单中的流程、规则和权限 | 技术设计所需交互或服务行为明确，评审变更已回写需求 |
| 技术设计 | 已确认需求、非功能约束及原型 | 估算与计划覆盖实现方案、依赖和风险；已有实现偏差已处理 |
| 工作量与成本估算 | 功能范围、技术方案、工作分解与成本依据 | 资源、预算、报价和计划口径相符，无遗漏或重复计算 |
| 项目计划及联合确认 | 前线要求、方案、估算、资源和依赖 | 任务可承接工作包与里程碑，交付与验收安排一致，授权有依据 |
| 开发任务列表 | 已确认需求、方案、估算与项目计划 | 实现及验证工作完整，任务责任与依赖可执行；估算变化已回报 |
| 实现及实施总结 | 任务、需求、原型与技术设计 | 实际完成和差距有证据，测试范围与环境可承接 |
| 测试报告 | 需求判据、功能范围、实现版本和测试证据 | 发布范围与达标结论一致，缺陷及未覆盖项不被隐藏 |
| 发布记录 | 测试结论、交付计划与授权记录 | 实际可用版本、功能及交付结果可核验，支持后续效果检验 |
| 迭代复盘 | 原定目标、发布结果、运行数据和客户反馈 | 改进项回写受影响的需求、方案、估算、计划及下一轮任务 |

## 5. 一组相互衔接的写作示例

以下仅为虚构的写作示例，不是可默认带入项目的业务规则。

**示例输入**：借用人提交申请后状态为待审批，可查看自己的处理结果；只有设备管理员可审批，选择通过后状态为已通过，填写原因后可驳回为已驳回，借用人可见原因；缺少驳回原因时应提示且状态不变。首版不支持批量审批，并发审批规则尚未确认。

**总体与分类**：系统支持设备借用申请及审批。按使用者划分为借用人端和设备管理后台，分别支持申请提交与审批处理；共用同一申请记录。

**功能清单中的子功能 FUN-02：申请审批**

设备管理员在管理后台查看待审批申请，并逐笔选择通过或驳回。处理后，借用人能够查看结果；驳回结果包含原因。首版不包含批量审批。业务规则见 REQ-02；并发处理规则列入 Q-01，待确认后补齐。

**需求规格中的子需求 REQ-02：处理借用申请**

设备管理员处理处于待审批状态的借用申请。该要求来源于示例输入，关联 FUN-02。

- 正常处理：选择通过时，申请变为已通过；选择驳回并填写原因时，申请变为已驳回并保留原因。
- 校验与权限：借用人不能执行审批；驳回原因缺失时不提交审批结果，申请保持待审批状态。
- 验收：用借用人身份操作时不能审批；管理员填写原因驳回后，借用人可见驳回结果与原因；原因缺失时状态不变。
- 待确认 Q-01：两个管理员同时处理同一申请时如何判定结果。由业务代表与架构师确认，影响并发处理及对应测试；本稿不推定先提交优先等规则。

**原型与测试的承接**：原型展示待审批申请、单笔处理以及缺少驳回原因的提示；用例 TC-02 验证缺少原因时状态不变。没有实际运行记录时，用例写“待执行”，测试报告不能写“通过”。

“支持审批，权限完善，异常友好”没有交代可验证行为。上述写法把业务结果、边界、判据与未知项分开，功能清单仍保持简短，详细规则只在需求规格定义。

## 6. 输出完成标准

交付前实际检查以下六项，不以勾选代替内容质量：

- **有用**：开头能让读者知道要判断什么、采取什么行动。
- **清楚**：先总后分，分类口径统一，复杂内容有子章节与段落。
- **具体**：重要需求有行为与判据，方案有取舍依据，计划有责任与条件，报告有实际结果。
- **可信**：事实、目标、假设和确认状态可区分，结论没有超出证据。
- **一致**：范围、编号、指标、估算和版本前后相符，主记录明确，无重复定义。
- **可接续**：下一环节可以据此开展工作；未决事项明确，阻塞条件没有被隐藏。

完成后删除编写提示、示例占位、空表和无内容的章节。缺失核心信息时交付明确标记的待评审稿及具体缺口，不伪装为最终成果；确无问题或差距时据实说明，不为凑齐栏目制造问题。
